# Delta: llm-contracts (stage-5-llm-contracts)

## MODIFIED Requirements

### Requirement: Риск-блокер транспорта решается до кода (день 1 этапа)

Проверка `response_format: json_schema strict` выполняется **per-relay**;
response_format включается на релее только после эмпирического вердикта
enforces на этом релее. Статус на 2026-08-21:

- **Chattiq** (LiteLLM `chattiq.ru/v1`, chat/completions, gpt-5.6-sol через
  прямой OpenAI) — **enforces** (проба 2026-08-21: ломающий промпт подавлен,
  схема соблюдена; `json_object` недостаточен — лишние поля остаются;
  served_model сверен — silent-downgrade не было). Транспорт дев/приёмки.
- **kie** (обе ветки `gpt_api.py:2119-2145`) и **vibecode** — не проверены
  (нет ключей заказчика); до положительного вердикта работают в деградации:
  реестр схем + repair-retry без response_format.

#### Scenario: Релей с вердиктом enforces
- **WHEN** вызов мигрированного агента идёт через релей со статусом enforces
- **THEN** схема реестра прокидывается в `response_format` (chat) /
  `text.format` (responses); клиентская валидация и repair-retry остаются
  включёнными

#### Scenario: strict + адаптивное дробление
- **WHEN** вызов раздроблен 1→2→4 (`_chat_adaptive_1_2_4`) — каждая половина
  схемно-валидна, но неполна
- **THEN** полнота (coverage N/N uuid) валидируется ПОСЛЕ склейки
  `_merge_packed_apply_ops`; схемная валидность части не считается успехом
  целого

#### Scenario: Непроверенный или не держащий релей
- **WHEN** релей не проверен либо игнорирует/отвергает response_format
- **THEN** деградация: тот же реестр схем + централизованный repair-retry
  без response_format; функциональность мигрированных агентов не меняется,
  меняется только частота repair

## ADDED Requirements

### Requirement: Двухрежимный транспорт structured outputs

Транспорт SHALL поддерживать режим structured outputs `auto|on|off`
(настройка, default `auto` = по per-relay вердикту). Клиентская
Pydantic-валидация и repair-политика SHALL выполняться во всех режимах:
response_format — оптимизация частоты ошибок, не замена валидации.

При использовании LiteLLM-шлюза как релея пайплайна кросс-модельный silent
fallback (`default_fallbacks`) SHALL быть отключён для ключа пайплайна либо
детектироваться клиентски (сверка `model` ответа с запрошенной); ответ от
подменённой модели на мигрированном пути = ошибка транспорта, не вход
валидации.

#### Scenario: Ответ от подменённой модели
- **WHEN** шлюз вернул 200, но `model` ответа ≠ запрошенной (fallback шлюза)
- **THEN** ответ не передаётся в валидацию контракта; вызов считается
  ошибкой транспорта и ретраится по обычной политике chat(). Транспорт
  SHALL нести фактическую модель ответа в `GptChatResult` (сейчас поле
  заполняется запрошенной моделью)

#### Scenario: Обрыв ответа в контрактном режиме
- **WHEN** strict-вызов оборван (Cloudflare/сеть), текст выглядит
  усечённым
- **THEN** CF-continuation НЕ используется (строковая склейка несовместима
  со strict-JSON); попытка считается невалидной → обычный ретрай целого
  вызова; continuation остаётся только для неконтрактных вызовов

#### Scenario: Volume-добор в контрактном режиме
- **WHEN** после частичного apply-ops запускается добор недостающих uuid
  (`volume_complete`)
- **THEN** рекурсивный вызов добора наследует контракт вызова-родителя и
  валидируется той же схемой; недобор до N/N = ошибка, не warning+break
