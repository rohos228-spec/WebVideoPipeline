# cost-accounting Specification

## Purpose

Стоимость текстовых LLM видима по проектам/нодам/моделям, включая неуспешные
вызовы; прогон имеет бюджет-предохранитель. Закрывает аудит §3: usage
парсится и выбрасывается; при склейках теряется кратно; полей стоимости в БД
нет; ретраи вложены в 5 слоёв, не знающих друг о друге. Этап 3 контракта
(в любой момент).

As-is (карта §4.1): один транспорт `gpt_api.chat()` покрывает все 41
call-site; contextvar project/node/model уже существует
(`llm_override.py`); слои ретраев: chat ×4 → adaptive 1→2→4 → continuation
×2 → volume-добор → batch-политики.

## Requirements

### Requirement: Один хук учёта в gpt_api.chat()

Каждый HTTP-вызов LLM SHALL записываться одним хуком в `chat()`
(`gpt_api.py:2052`) — включая ретраи, доборы, continuation и НЕуспешные
вызовы. Контекст project/node/model берётся из contextvar
(`llm_override.py`); call-site'ы не меняются.

#### Scenario: Неуспешный вызов
- **WHEN** вызов упал по timeout/429/500 после N ретраев
- **THEN** каждый фактический HTTP-запрос записан с результатом и usage
  (если вернулся); стоимость ретраев видна отдельно от успеха

#### Scenario: Вложенные слои
- **WHEN** adaptive split дробит вызов 1→2→4
- **THEN** записаны все 7 фактических вызовов, связанные одним
  logical_call_id — видно, во что обошёлся один логический запрос

Модель записей: llm_calls хранит ОДНУ строку на фактический HTTP-вызов;
«стоимость логического вызова/ноды/прогона» — всегда агрегат
(SUM по logical_call_id / node_key / project_id), отдельных строк-сумм нет.

#### Scenario: Вызов без usage в ответе
- **WHEN** вызов упал по timeout/обрыву без тела ответа
- **THEN** строка пишется с tokens=NULL и флагом unbilled; в агрегатах
  показывается отдельно («N вызовов без usage»); критерий сходимости с
  биллингом применяется только к строкам с usage

#### Scenario: Отказ контракта виден учёту
- **WHEN** HTTP-вызов успешен (200, валидный JSON), но контракт
  ([[llm-contracts]]) отверг ответ и запустил repair
- **THEN** строка вызова дополняется исходом `contract_rejected` (колбэк
  политики контрактов → учёт); «доля неуспешных» включает такие вызовы,
  а не только HTTP-ошибки

### Requirement: usage суммируется на склейках

При склейке частичных ответов (adaptive merge `gpt_api.py:1844`,
continuation `:2261-2320`, volume-добор) итоговый usage SHALL равняться
сумме usage частей (as-is: `usage=first.usage` — теряется кратно).

#### Scenario: Continuation ×2
- **WHEN** ответ собран из 3 кусков (исходный + 2 «продолжи»)
- **THEN** usage записи = сумма трёх, не первого

### Requirement: Таблица llm_calls + прайс-таблица

БД SHALL содержать таблицу `llm_calls`: project_id, node_key, model, релей,
prompt/completion/total tokens, стоимость по прайс-таблице моделей,
result (ok/error/retry), logical_call_id, prompt_version_hash, created_at.
Прайс-таблица моделей — конфиг в репо; неизвестная модель учитывается с
нулевой ценой и warning (не падает).

#### Scenario: Версия промпта
- **WHEN** мастер-промпт ноды изменён
- **THEN** новые записи несут другой prompt_version_hash — стоимость и
  качество версий сравнимы задним числом

### Requirement: Бюджет-предохранитель на прогон

Проект SHALL иметь бюджет (default из конфига); при превышении суммы
стоимостей llm_calls прогона проект переходит в `paused` с причиной
«бюджет исчерпан: $X из $Y» до решения оператора.

#### Scenario: Разгон ретраев
- **WHEN** петля проверок/ретраи разогнали стоимость прогона выше бюджета
- **THEN** pause с причиной вместо бесконечного жора (сочетается с лимитом
  регенераций из [[checks-cascade]])

### Requirement: Стоимость по нодам видна в UI

Студия SHALL показывать по прогону: суммарную стоимость, разбивку по
нодам/агентам и моделям, долю неуспешных вызовов.

#### Scenario: Дорогая нода
- **WHEN** оператор открывает прогон
- **THEN** видно, что (например) vision-проверки стоят 60% прогона —
  основание для решений об оптимизации (prompt caching — роадмап)

## Открытые вопросы к заказчику (до старта этапа 3)

1. **Langfuse:** заголовок этапа в WORK_PLAN — «через Langfuse», содержание —
   самописная llm_calls. Рекомендация: source of truth — llm_calls в
   проектной SQLite (Windows-локальный стек заказчика, лишний сервис — боль);
   Langfuse — опциональный экспорт-sink поверх, если заказчик захочет.
   Зафиксировать до старта.
2. **Дашборд в UI:** входит в $300 этапа минимальной страницей (таблица по
   нодам + сумма прогона в студии) — подтвердить объём; красивая аналитика —
   отдельно.

## Acceptance (критерий этапа)

Стоимость ролика по агентам видна в UI, включая неуспешные вызовы; цифры
сходятся с биллингом релея на тестовом прогоне по строкам с usage (допуск —
округление прайса; вызовы unbilled показаны количеством).
