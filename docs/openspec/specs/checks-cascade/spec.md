# checks-cascade Specification

## Purpose

Проверки контента сходятся за ограниченное число регенераций, не зеленеют без
провайдера, отсекают брак дешёвыми проверками до платного LLM-vision и не
фиксируют принятие навсегда по одной галлюцинации. Закрывает аудит §4 и
находки §5/§9 карты ([system-map](../../system-map.md)).

As-is (карта §5): 4 несогласованных контура (К1 vision_check_loop — живой;
К2 auto_review — мёртв для картинок, промпты под .gitignore; К3
gpt_verdict_review; К4 post_step_validate). Спекуется контур К1 + врезка
media_probe; унификация К2/К3 — вне текущей сметы (роадмап).

Статус: Requirement 1 внедрён (этап 0). Requirements 2-8 — target этапа 4.

## Requirements

### Requirement: Проверка без провайдера не зеленеет (fail-closed) [ВНЕДРЕНО]

Без API-ключа (`settings.gpt_api_enabled` = false) check-роли (`review`,
`gate`, `compare`, `check_mode=True`) SHALL завершаться ошибкой, а не
stub-вердиктом. Stub-путь проверок — только по явному опт-ину
`VP_ALLOW_STUB_CHECKS=1` (dev/tests).

#### Scenario: Нет ключа в проде
- **WHEN** `run_operator_api` вызван с check-ролью без ключа и без опт-ина
- **THEN** `RuntimeError` с пометкой fail-closed; вердикт не создаётся

#### Scenario: Dev/tests с опт-ином
- **WHEN** то же с `VP_ALLOW_STUB_CHECKS=1`
- **THEN** прежний детерминированный stub-вердикт

Implementation: `gpt_operator_client.py` (после ветки `gpt_api_enabled()`),
`app/settings.py`, `tests/test_operator_fail_closed.py`. Change:
`stage-0-security-hygiene`.

### Requirement: Лимит регенераций из конфига, исчерпание = громкая пауза

Лимит кругов vision-регенерации SHALL браться из конфига (default 2).
При исчерпании проект SHALL переходить в `paused` с машиночитаемой причиной
и уведомлением, а не молча вставать на `*_ready`.

Default 2 — стартовое значение из запрета владельца (HANDOVER); фактический
порог калибруется живыми прогонами этапа 4 (если после фиксов осей петля
типично сходится за 3 — default поднимается решением заказчика, не кодом).

#### Scenario: Исчерпание кругов
- **WHEN** круг регенерации превышает лимит (сейчас: 20 хардкодом,
  `vision_check_loop.py:39`; тихий выход `:615-624`)
- **THEN** проект в `paused`, причина «vision-лимит исчерпан, кадры N…»
  в meta, уведомление в Telegram; сквозной счётчик кругов живёт в
  `Project.meta` (рядом с существующим vision_check-блоком) и переживает
  рестарты/повторные запуски check-ноды; НЕ обнуляется до явного решения
  оператора

#### Scenario: Оператор решает
- **WHEN** оператор снимает паузу с решением «ещё N кругов» или «принять как есть»
- **THEN** решение логируется; «принять как есть» помечает кадры
  `accepted_by_operator`, а не `vision_check_passed`

### Requirement: Вердикт всех осей доезжает до промпта регенерации

Замечания проверки по КАЖДОЙ оси брака (style, character, logic, format,
pose, clones, text, angles, quality, hands) SHALL преобразовываться в правку
промпта регенерации — для всех kind (scenes, hero, videos) и всех shot.

As-is: только `character` и `clones`, только shot 1, только scenes
(`vision_regen_fix.py:23-35`, `:213`; `vision_check_loop.py:571`); ось
`logic` отсутствует в шаблоне scores (`check_analysis.py:235-245`).

#### Scenario: Брак по не-покрытой сейчас оси
- **WHEN** вердикт содержит `[critical] frame_007: руки — шесть пальцев`
- **THEN** промпт регенерации кадра 007 отличается от исходного и содержит
  корректирующую инструкцию по оси hands

#### Scenario: Брак на shot 2 / на hero / на видео
- **WHEN** critical-замечание относится к shot 2, hero-референсу или клипу
- **THEN** правка промпта применяется тем же механизмом (не no-op)

#### Scenario: Регенерация без изменений запрещена
- **WHEN** цикл собирается перегенерировать кадр тем же байт-в-байт промптом
  без правок
- **THEN** это логируется как ошибка петли (метрика несходимости), а не
  выполняется молча. (Идентичность промпта — необходимый минимум; сравнение
  идентичности результата (perceptual hash кадра) — кандидат роадмапа, не
  этап 4.)

### Requirement: Каскад дёшево→дорого (media_probe перед vision)

Технические пре-чеки (файл читается ffprobe, длительность > 0, aspect
соответствует проекту, не-нулевой размер картинки; для аудио — не-тишина)
SHALL выполняться ДО отправки артефакта в LLM-vision. Брак по пре-чеку не
доходит до платного vision и сразу даёт regen-цель с кодовой причиной.

Точки врезки (карта §5.3): `enrich_xlsx.py:735` (финальный список файлов),
`enrich_xlsx.py:756-765` (mp4 до нарезки в стиллы),
`generate_videos.py:600-640/:700-740` (перед Artifact),
`generate_images.py:1114` (перед image_generated).

Объём работ по модулю: в `media_probe.py` сейчас только `probe_video_size`
и `probe_duration` — проверки aspect PNG, минимального размера картинки и
тишины аудио ДОБАВЛЯЮТСЯ в этот же модуль в рамках этапа 4 (это часть
сметы этапа, не «уже есть»).

#### Scenario: Битый клип
- **WHEN** mp4 не читается ffprobe или длительность 0
- **THEN** кадр помечается на regen с причиной `media_probe:*` без vision-вызова

#### Scenario: Дубль probe_duration устранён
- **WHEN** `video_sheet` нарезает стиллы для проверки
- **THEN** длительность берётся из `media_probe.probe_duration`; ошибка
  пробы — это ошибка, а не молчаливые 8.0 c (as-is: `video_sheet.py:64,80-86`)

### Requirement: Конфликт гейта решается в пользу fail

При расхождении сохранённого gateStatus и свежего вердикта по одному отчёту
SHALL побеждать fail.

As-is наоборот: `vision_check_loop.py:515-523` — meta `pass` + свежий `fail`
→ берётся `pass`.

#### Scenario: Расхождение источников вердикта
- **WHEN** meta-гейт говорит pass, разбор текста отчёта даёт fail
- **THEN** цикл работает по fail; расхождение логируется

### Requirement: Принятие кадра пересматриваемо

Отметка «кадр принят» SHALL: (а) ставиться только из отчёта с общим
`verdict: pass` либо явным `[ok]` при непротиворечивом гейте; (б) сбрасываться
при изменении промпта/входа кадра; (в) НЕ ставиться кадрам, которые модель
не упомянула.

As-is: `[ok]` фиксируется даже из fail-отчёта (`vision_check_loop.py:526`),
неупомянутые кадры автоматически passed (`:858-888`), passed-кадры больше
никогда не показываются модели (`:802-855`) — замкнутый круг.

#### Scenario: [ok] в провальном отчёте
- **WHEN** отчёт с `verdict: fail` содержит `[ok] f3`
- **THEN** f3 не помечается принятым навсегда; он попадает в следующий
  recheck вместе с regen-целями

#### Scenario: Неупомянутый кадр
- **WHEN** отчёт не упоминает кадр f9 ни в ok, ни в critical
- **THEN** f9 остаётся непроверенным (идёт в следующий recheck), а не
  принятым; повторные recheck непроверенных кадров считаются в тот же
  сквозной лимит кругов — вечного платного recheck нет (на лимите — pause
  с перечнем непроверенных)

#### Scenario: Смена промпта кадра
- **WHEN** `Frame.image_prompt` изменён (db_patch или вручную)
- **THEN** отметка принятия этого кадра сбрасывается

### Requirement: Отчёт без оценок не проходит автоматом

Отчёт проверки без `overall`-балла и без critical SHALL трактоваться как
неполный (ошибка контракта → repair-retry, см. [[llm-contracts]]), а не как
`pass` (as-is: `check_analysis.py:820-824`).

#### Scenario: severity-only отчёт
- **WHEN** ответ модели содержит только текстовые замечания без scores
- **THEN** запускается repair-retry с требованием формата; авто-pass нет

### Requirement: Regen-цели извлекаются без ложных срабатываний

Идентификация кадров на регенерацию SHALL опираться на явные токены
(`f7`, `f7s2`, uuid), а не на любые числа рядом со словом «кадр»
(as-is: `\b(\d{1,4})\b`, `check_analysis.py:875-921`).

#### Scenario: Число в тексте замечания
- **WHEN** critical-замечание содержит «на фоне 3 фигуры» для кадра f7
- **THEN** regen-цель — только f7; кадр 3 не трогается
