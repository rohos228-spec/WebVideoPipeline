# cache-resume Specification

## Purpose

Результат единицы работы привязан к хэшу её входа; падение/рестарт/STOP
доезжают с места остановки за стоимость остатка; смена промпта инвалидирует
ровно конус зависимостей. Закрывает аудит §2. Этап 2 контракта (исполняется
3-м, ПОСЛЕ [[llm-contracts]]: «вход» для хэша определяется контрактом).

As-is (карта §1-3, §6, §8): состояние = один enum `Project.status`; рестарт
процесса откатывает статус (`startup_guard.py:70-187`); кэш по входу — только
ASR; чекпоинты img_pr/scene_design короткозамыкают по имени/uuid БЕЗ проверки
входа; INFLIGHT-маркеры без TTL/owner (`img_streams.py:20-21`); в репо 4
реконсайлера + 10 recover_*-функций — система регулярно реконструирует
состояние по диску.

## Requirements

### Requirement: input_hash на единицу работы

Каждая единица LLM/медиа-работы (NodeRun, батч, кадр-генерация) SHALL хранить
`input_hash = hash(нормализованный вход + версия промпта + модель +
параметры генерации)`. Место хранения: `NodeRun.meta` / `Frame.attrs`
(существующие JSON-колонки, без новых таблиц).

#### Scenario: Повтор с тем же входом
- **WHEN** шаг перезапущен, input_hash единицы работы совпадает с сохранённым
  при успешном результате
- **THEN** результат переиспользуется без LLM/медиа-вызова; в логе — cache hit

#### Scenario: Вход изменился
- **WHEN** мастер-промпт/модель/вход изменены (hash не совпал)
- **THEN** чекпоинт единицы инвалидируется, работа выполняется заново;
  «протухший» результат не подтягивается (as-is подтягивается: чекпоинты
  img_pr/scene_design по имени, аудит §2)

### Requirement: Явный граф зависимостей шагов

Конус зависимостей SHALL задаваться явной декларацией (константа
`STEP_DEPENDENCIES` рядом с `node_registry.py` либо таблица) — НЕ выводиться
из `_STATUS_ORDER` (`menu.py:137-142` содержит коллизии ord:
music_ready=36=sfx_planning и др., карта §9#3) и не из if/elif диспетчера.
`WorkflowRun.nodes_snapshot` — snapshot для UI, не DAG-источник.

#### Scenario: Однозначность конуса
- **WHEN** нужно определить, что пересчитывать при смене входа шага X
- **THEN** ответ читается из STEP_DEPENDENCIES; для шагов с коллизией ord
  (music/sfx/assemble) конус определён корректно

### Requirement: Инвалидация ровно конуса зависимостей

Смена входа узла SHALL инвалидировать его результат и результаты только
зависимых от него узлов (по STEP_DEPENDENCIES), не трогая независимые.

#### Scenario: Смена промпта img_pr
- **WHEN** оператор меняет мастер-промпт img_pr
- **THEN** пересчитываются image_prompt кадров и всё ниже (images → anim_pr →
  videos); закадр, split, scene_design, hero остаются в кэше

### Requirement: Версия промпта — контентный хэш, единый с учётом

«Версия промпта» в input_hash SHALL быть sha256 содержимого промпта в момент
вызова (файл из prompts/ + вшитые хинты кода), НЕ git-ревизией (prompts/*
под .gitignore, история squash-нута). Тот же хэш SHALL использоваться как
`prompt_version_hash` в llm_calls ([[cost-accounting]]) — два учёта одного
промпта не расходятся.

#### Scenario: Правка промпта вне git
- **WHEN** оператор правит файл промпта локально
- **THEN** input_hash зависимых единиц меняется (инвалидация срабатывает),
  и записи llm_calls несут новый prompt_version_hash

### Requirement: Кэшируются только полные принятые результаты

Cache hit SHALL выдаваться только по единицам, чей результат был принят
полностью: результат с маркером `_salvaged_partial` или батч, применённый
до падения соседнего батча (commit-per-batch, `enrich_xlsx.py:1063`),
кэшем НЕ считается — при рестарте такие единицы доезжают добором/повтором.

#### Scenario: Salvage не кэшируется
- **WHEN** прошлый прогон принял salvage обрезанного JSON
- **THEN** рестарт не короткозамыкает эту единицу по хэшу — она
  перепроверяется/добирается до полного покрытия

### Requirement: Рестарт различает resume и recovery

startup_guard SHALL вместо отката помечать «running без владельца»
(осиротевший lease) и передавать управление resume; реконсайлеры
(карта §8), построенные на «рестарт = откат», переводятся на этот контракт
в том же change (их список — часть tasks этапа 2). Признак различения:
живой/просроченный lease + курсор, а не сам факт рестарта.

#### Scenario: Рестарт при живом прогрессе
- **WHEN** процесс перезапущен, у шага есть курсор и просроченный lease
- **THEN** шаг продолжает с курсора; статус не откатывается; recovery-скан
  (диск→БД) выполняется ДО продолжения, как и сейчас

### Requirement: Персистентный курсор прогресса шага

Прогресс внутри шага (какие батчи/кадры завершены) SHALL персиститься так,
чтобы рестарт процесса продолжал с курсора. Рестарт SHALL NOT откатывать
`Project.status` назад: startup_guard вместо отката помечает «running без
владельца» и передаёт решение resume-механизму.

#### Scenario: Kill -9 на 80% шага
- **WHEN** процесс убит посреди generating_images с 40/50 готовых кадров
- **THEN** после рестарта шаг продолжает с кадра 41; повторной оплаты 40
  готовых нет

#### Scenario: STOP оператора
- **WHEN** оператор жмёт STOP посреди шага
- **THEN** курсор сохранён; продолжение — с места остановки, не с нуля шага

### Requirement: Lease с TTL и владельцем (атомарный захват в БД)

Захват единицы работы SHALL оформляться записью в выделенной таблице
`work_leases` (project_id, unit_key, owner, expires_at; unique(project_id,
unit_key); индекс по expires_at) в основной SQLite (WAL + busy_timeout
уже включены, `app/db.py`). Захват — ОДИН атомарный оператор с проверкой
rowcount: `INSERT ... ON CONFLICT(project_id, unit_key) DO UPDATE SET
owner=:me, expires_at=:new WHERE expires_at < :now` — никаких
read-then-write. `owner` = host:pid:task_uuid (per-asyncio-task uuid, не
голый pid: воркер — один процесс со многими конкурентными задачами).
Отмена/завершение задачи освобождает lease в finally; отменённая без
finally задача теряет lease по TTL.

Файловый `montage_lane_claim` (`montage_coexist.py:17-59`) НЕ образец для
per-unit lease: mtime-TTL и гонка is_file→write, однополосный. Он остаётся
как есть для монтажной полосы. Заменяются: голые
`img_gen_inflight`/`video_gen_inflight` (`img_streams.py:20-21`) и
in-process `_SPLIT_LOCK` (`step_global_lock.py:14-35`). Опция при
contention с основным writer («database is locked» ретраи уже есть в коде)
— вынести в отдельный `lease.db`; решение фиксируется в proposal этапа 2
по замеру.

#### Scenario: Два процесса, один просроченный lease
- **WHEN** два процесса одновременно пытаются перехватить кадр с истёкшим
  lease
- **THEN** UPDATE-захват проходит ровно у одного (rowcount=1); второй
  получает rowcount=0 и пропускает — двойной генерации нет

#### Scenario: Две asyncio-задачи одного процесса
- **WHEN** две задачи одного воркера претендуют на один кадр
- **THEN** owner различает их по task_uuid; кадр берёт одна

#### Scenario: Умерший владелец
- **WHEN** процесс-владелец умер, lease истёк
- **THEN** кадр перехватывается атомарным захватом без ручного вмешательства

### Requirement: Один канонический воркер

Poll-цикл SHALL подниматься из одного канонического пути
(`pipeline_worker.ensure_pipeline_worker_started`); legacy-воркер
`app/worker.py` (собственный урезанный ACTIVE_STATUSES :29-47) выводится из
эксплуатации или редиректится на канонический. Список активных статусов —
один (закрывает и находку §9#1 карты: sfx-статусы, отсутствующие в
`main.py:300-321`).

#### Scenario: Запуск legacy-точки
- **WHEN** оператор/скрипт запускает `python -m app.worker`
- **THEN** поднимается канонический цикл (или процесс завершается с
  указанием на канонический путь) — второго конкурирующего цикла нет

## Acceptance (критерий этапа)

Убитый на 80% прогон доезжает рестартом за стоимость остатка (проверяется по
[[cost-accounting]], если этап 3 уже сделан, иначе по счётчику вызовов);
смена промпта пересчитывает ровно конус зависимостей.
