# llm-contracts Specification

## Purpose

Каждый LLM-выход на P0-путях проходит через типизированный контракт
(Pydantic v2) с единой политикой ошибок и repair-retry — вместо 110 алиасов,
8 самописных JSON-экстракторов и четырёх несовместимых поведений при ошибке.
Закрывает жалобу «постоянно ошибки валидации» (аудит §1; карта §4).
Этап 5 контракта (исполняется 2-м, до кэша: контракт определяет «вход» для
input_hash из [[cache-resume]]).

As-is (карта §4.2-4.4): 25 логических агентов, 41 call-site; Pydantic на
LLM-путях = 0; эталонный контур `ai_result_io.text_job` (87-140) использует
1 агент из 25.

**Приёмочное множество этапа 5 («5 мигрированных агентов» из WORK_PLAN),
единая трактовка** — пять позиций:
1. A12 apply-ops ядро (+ A14 character_registry — тот же путь);
2. A3 split;
3. scene_design-комплекс как ОДНА позиция (A5 skeleton + A6 editor +
   A7-A10 категорийные + A11 assemble);
4. A15 img_pr;
5. типизация отчётов check-нод (A17, схема CheckReport).

Кандидаты следующей очереди (не в приёмке этапа, опция «+$500 все
остальные»): A13 scene_grammar, A16 anim_pr, A1/A2 plan/script. Это
множество фиксируется в proposal этапа 5; менять его — только решением
заказчика до старта кода.

## Requirements

### Requirement: Риск-блокер транспорта решается до кода (день 1 этапа)

До фиксации дизайна SHALL быть эмпирически проверено на каждом релее
(kie, vibecode, VPS-relay), поддерживает ли он `response_format:
json_schema strict` в обеих ветках транспорта (`gpt_api.py:2119-2145`:
responses + chat/completions).

#### Scenario: Релей поддерживает
- **WHEN** тестовый вызов с json_schema strict возвращает валидный объект
  по схеме на всех используемых моделях
- **THEN** дизайн: схемы реестра прокидываются в `response_format` через
  `chat()` / адаптивный split / pdf-chunks / ApiGptClient

#### Scenario: strict + адаптивное дробление
- **WHEN** вызов раздроблен 1→2→4 (`_chat_adaptive_1_2_4`) — каждая половина
  схемно-валидна, но неполна
- **THEN** полнота (coverage N/N uuid) валидируется ПОСЛЕ склейки
  `_merge_packed_apply_ops`; схемная валидность части не считается успехом
  целого

#### Scenario: Релей не поддерживает
- **WHEN** релей игнорирует/отвергает response_format
- **THEN** дизайн деградирует: реестр схем + централизованный repair-retry
  без response_format; решение фиксируется в proposal этапа до начала кода

### Requirement: Реестр контрактов app/contracts/

Модуль `app/contracts/` (Pydantic v2) SHALL быть единственным источником схем
LLM-выходов: `ApplyOpsEnvelope`, `SkeletonPayload` + `SceneSlice`×4 (по
одному на активный категорийный агент A7-A10; sd_style снят с волн),
`AssemblePayload` (используется и A13 scene_grammar — тот же формат
{characters, scenes, ops, report}), `FrameSpec` (split), `ImgPrOps`,
`AnimPrOps`, `VoiceoverPayload`, `CheckReport` (vp.check.v1). 110 алиасов
(`db_apply.py:115-231`, `:240`) SHALL переехать в `validation_alias` схем.

Семантические ремонты db_apply — Хэмминг-ремонт uuid (:290) и
«номер вместо uuid» (:335) — СОХРАНЯЮТСЯ как pre-validation нормализация
ДО схемы (они дешевле repair-вызова LLM); ремонт логируется в meta единицы.

#### Scenario: Новое поле от модели
- **WHEN** модель возвращает поле-синоним (например «промпт_картинки» вместо
  «промт_картинки»)
- **THEN** поле маппится через validation_alias схемы, а не через словарь в
  db_apply; неизвестное поле — `LlmContractError` с именем поля

#### Scenario: Один контракт — все call-site
- **WHEN** два call-site потребляют один тип ответа (например apply-ops из
  enrich_xlsx и из orchestrator chat)
- **THEN** оба валидируют одной схемой из app/contracts/

### Requirement: Единая ошибка LlmContractError + одна repair-retry политика

Любой невалидный LLM-ответ на мигрированном пути SHALL подниматься как
`LlmContractError` (текст ошибки валидации внутри) и обрабатываться одной
политикой по образцу `ai_result_io.text_job:87-140`: (1) фидбек с текстом
ошибки в repair-промпт следующей попытки; (2) настраиваемый лимит попыток;
(3) отклонённые ответы сохраняются на диск; (4) исчерпание — fail-closed
raise, без тихого None и без частичного результата.

Заменяет 4 текущих поведения (карта §4.4): raise / warning+continue /
тихий None / fallback без LLM.

#### Scenario: Невалидный JSON
- **WHEN** ответ не парсится схемой
- **THEN** следующая попытка получает секцию «ошибки прошлой попытки» с
  текстом ошибки Pydantic; сырой ответ сохранён на диск

#### Scenario: Исчерпание попыток
- **WHEN** лимит repair-попыток исчерпан
- **THEN** `LlmContractError` наверх → step_failure_policy (pause), НЕ
  «зелёный» шаг

### Requirement: Запрет тихого частичного успеха

Мигрированный агент SHALL NOT молча принимать частичный результат или
подменять LLM-ответ эвристикой. Каждый известный тихий путь закрывается:

- img_pr `if all_ops: continue` (`xlsx_step_runners.py:948,:967`) — провал
  батча = ошибка батча;
- volume-добор `break` при ошибке (`volume_batches.py:296-305`) — недобор
  до N/N = ошибка;
- script fallback «весь ответ целиком» (`xlsx_step_runners.py:379-410`) —
  убрать; невалидный ответ = LlmContractError;
- split локальная разбивка (`:591-594`) и anim_pr локальный композер
  (`make_animation_prompts.py:104`) — допустимы только с явным маркером
  `degraded_no_llm` в NodeRun.meta и предупреждением оператору;
- salvage обрезанного JSON (`db_apply.py:367`) — допустим только с маркером
  `_salvaged_partial` И последующим добором до полного покрытия.

#### Scenario: Частичный батч img_pr
- **WHEN** батч N вернул невалидный ответ, батчи 1..N-1 успешны
- **THEN** шаг не зеленеет; батч N уходит в repair-retry; итоговый гейт
  требует покрытия N/N кадров

#### Scenario: Транзакционная граница батчей
- **WHEN** commit-per-batch (`enrich_xlsx.py:1063`) применил 1..N-1, батч N
  упал окончательно
- **THEN** применённые батчи остаются в БД (откат не требуется — записи
  идемпотентны по uuid), но шаг помечен незавершённым; повтор шага добирает
  только недостающее; кэш-правило — см. [[cache-resume]] «только полные
  принятые результаты»

#### Scenario: Деградация без LLM
- **WHEN** сработал локальный fallback (split/anim_pr)
- **THEN** NodeRun.meta несёт `degraded_no_llm: true`, оператор видит это
  в UI/уведомлении; harness-гейт вправе не пропустить дальше

### Requirement: Битый ответ проверки ≠ вердикт fail

Невалидный/чужой/неполный JSON от проверяющей ноды SHALL давать
`LlmContractError` и repair-retry, а не молчаливый `verdict: fail`
(as-is: `check_analysis.py:1334, :1346, :1351` — три тихих пути,
неотличимых от реального брака, каждый запускает платный regen-цикл).

#### Scenario: Мусорный ответ проверки
- **WHEN** проверка вернула текст без vp.check.v1-структуры
- **THEN** repair-retry с текстом ошибки; regen-цикл НЕ запускается от
  ошибки формата

### Requirement: Шаблон миграции для остальных агентов

По итогам миграции P0 SHALL существовать инструкция + шаблон (в
`docs/openspec/`) для переноса остальных агентов силами кодеров заказчика:
как объявить схему, как врезать политику, как тестировать на живой задаче.

#### Scenario: Чужой разработчик мигрирует агента
- **WHEN** разработчик заказчика берёт немигрированный агент (например A21 music)
- **THEN** по шаблону он добавляет схему и политику без чтения всей кодовой базы

## Вне бюджета этапа (зафиксировать с заказчиком)

- A24 orchestrator chat исполняет apply-ops прямо из свободного чата
  (`db_browser.py:2257-2270`): схемная валидация НЕ решает авторизацию —
  структурно валидная деструктивная операция пройдёт. Рекомендация
  заказчику: явное подтверждение перед исполнением ops из чата (или
  read-only режим). Миграция A24 на контракты — вне приёмочного множества.
- Не-P0 агенты продолжают стопорить конвейер через Project.status как
  сейчас — этап 5 этого не меняет и не обещает.

## Acceptance (критерий этапа)

Серия ≥10 живых прогонов на реальных темах: 0 `LlmContractError` после
исчерпания repair-попыток на приёмочном множестве (см. шапку) И
repair-rate ≤ порога, зафиксированного в proposal этапа (repair-попытки —
платные; «0 ошибок за счёт 5 repair на каждый вызов» приёмкой не считается —
метрика из llm_calls, [[cost-accounting]], либо из логов политики до
этапа 3).
