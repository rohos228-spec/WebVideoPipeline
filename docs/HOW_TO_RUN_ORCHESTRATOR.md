# Как запустить чат-оркестратор

## Что он делает

Чат-оркестратор — это чат в студии, через который оператор управляет проектами обычными словами.
- Чат разбирает просьбу, планировщик (LLM) собирает план действий, а критик проверяет этот план.
- Действия, которые стоят денег (картинки, видео, озвучка, монтаж), сначала показываются карточкой с ценой и запускаются только после одобрения.
- Через чат можно запускать проекты и целые пачки через очередь, продолжать пайплайн с нужного шага, менять настройки, получать отчёты по проектам и расходам.
- В режиме учётных записей каждый пользователь видит и меняет только данные своего арендатора (tenant).

## Переменные окружения

Ниже только имена. Значения хранятся в `.env` (файл в `.gitignore`), в репозиторий их не кладём.

LLM для чата
- `VIBECODE_API_KEY`, `VIBECODE_BASE_URL` — нужны планировщику чата (модель из каталога `gpt-5.6-sol-vibecode`). Без ключа планировщик отказывается работать (`key_missing`).
- `TEXT_LLM_PROVIDER` (`kie` | `vibecode`), `KIE_API_KEY`, `GPT_API_KEY`, `GPT_BASE_URL`, `GPT_MODEL` — текстовые узлы пайплайна.
- `PAY52_BASE_URL`, `PAY52_GPT_KEY`, `PAY52_CLAUDE_LOW_KEY`, `PAY52_CLAUDE_HIGH_KEY`, `PAY52_GLM_KEY` — модели 52pay из каталога.

База данных
- `DATABASE_URL` — если пусто, используется SQLite по `SQLITE_PATH` (по умолчанию `./data/state.db`). Если задано, то это Postgres вида `postgresql+asyncpg://...` с изоляцией арендаторов через RLS.
- `DB_POOL_SIZE`, `DB_MAX_OVERFLOW` — размер пула для Postgres.

Учётные записи и арендаторы
- `STUDIO_SESSION_SECRET` — если пусто, студия работает в режиме владельца (без входа и без арендаторов). Если задано, работает режим учётных записей, и каждый запрос должен нести токен.
- `SESSION_TTL_HOURS`, `SESSION_LEEWAY_SEC`, `TENANT_START_CREDITS`.
- `ALLOW_UNISOLATED_TENANTS` — разрешает арендаторов на SQLite. Нужно только для тестов, в проде не включать.

Лимиты расходов
- `ACTION_LAYER_SESSION_CAP_CREDITS` — потолок кредитов на одну сессию чата (0 — без потолка).
- `ACTION_LAYER_PLANNER_CALLS_PER_HOUR` — сколько раз в час можно вызвать планировщик (0 — без лимита).
- `LLM_BUDGET_USD` — бюджет на текстовые LLM.
- `FREE_TIER_ENABLED`, `FREE_TIER_SPEND_CAP_USD`, `FREE_TIER_MAX_PROJECTS` — бесплатный уровень.
- `CREDIT_USD_RATE`, `CREDIT_MARGIN` — пересчёт себестоимости в кредиты.

Параллельность и старт движка
- `WORKER_MAX_PARALLEL` — сколько проектов очереди крутятся одновременно. Значение ограничено `runtime_streams.WORKER_MAX = 10`: больше 10 не поставить ни через env, ни через чат, ни через ползунок в панели потоков (он идёт от 1 до 10).
- `CREATE_MAX_PARALLEL_OUTSEE` — отдельный пул вызовов API картинок Outsee, он остаётся 4. Потолок проектов на него не влияет: десять проектов делят те же четыре слота генерации.
- `ENGINE_STARTUP` (по умолчанию включено) — при старте закрывает задачи, прерванные рестартом, и запускает истечение просроченных одобрений.
- `ORCH_RECOVER_ON_START=1` — вместо закрытия поднимает прерванные задачи заново.

## Как запустить

1. Поставить зависимости бэкенда (Python 3.12): `pip install -e ".[dev]"`.
2. Собрать веб-интерфейс:
   ```
   cd web
   npm ci
   npm run build
   ```
   Сборка попадает в `web/out`, и бэкенд отдаёт её с корня. Папку `web/out` не коммитить.
3. Запустить бэкенд из корня репозитория: `python -m app.main`. На Windows можно через `STUDIO.cmd` (пункт 1).
4. Открыть http://127.0.0.1:8765, чат находится в студии.

## Миграции при старте

Схема обновляется сама при запуске бэкенда, руками ничего делать не нужно.
- `python -m app.main` вызывает `app/db_migrations.py::upgrade_to_head` (alembic `upgrade head`), и на SQLite, и на Postgres.
- На SQLite оркестратор дополнительно прогоняет свой раннер `app/orchestrator/db/migrations/*.sql` (`ensure_migrated`). На Postgres раннер только проверяет, что таблицы уже созданы alembic.
- Последняя миграция оркестратора — настоящий провайдер в журнале вызовов LLM `orch_llm_calls.provider`: допустимы `52pay`, `kie`, `vibecode`, `unknown` (раньше `vibecode` записывался как `52pay`). На SQLite это файл раннера `011_orch_llm_calls_provider.sql` (таблица пересобирается с теми же строками и индексами), в alembic это ревизия `0021` (на Postgres CHECK меняется на месте).
- Если бэкенд стартует без миграций (например, база Postgres поднята отдельно), выполнить `alembic upgrade head` из корня репозитория.

## Отчёт по данным работы с GPT

Просьба вида «сделай отчёт по данным работы с гпт: какие сцены и персонажи» выполняется действием `report.gpt_data`. Это чтение, бесплатно и без карточки одобрения.
- В отчёте таблица кадров (номер, закадровый текст, сцена, место, персонажи, действие и т.д.), список персонажей и список сцен. В чате таблица обрезается («Показаны первые N из M»), полная версия отдаётся ссылками на xlsx и html.
- Кадры берутся из базы, а если в базе их нет, то только для чтения из листа плана `project.xlsx`, без импорта.
- Если нода ещё не запускалась, отчёт честно пишет, что данных нет. Чужой проект арендатора не виден.

Колонки задаются в `app/services/action_layer/report_data_format.py`, код отчёта (`report_gpt_data.py`) их не знает. Как положить свой формат заказчика:
1. Если нужной колонки нет в `FRAME_COLUMNS`, добавить ключ: подпись и канонические поля кадра, из которых брать значение (берётся первое непустое). Канонические имена — как в `app/services/db_apply.py::FIELD_ALIASES`.
2. Добавить набор в `PRESETS`: имя и колонки по порядку.
3. Сделать его набором по умолчанию (`DEFAULT_PRESET`) или добавить слова в `PRESET_WORDS`, чтобы чат брал его по просьбе. `EXTRA_WORDS` добавляет колонку к любому набору («с промтами картинок»).

## Правка промта из чата

Правка идёт одним потоком, каждый шаг подтверждает человек.
1. Предложение. Просьба поправить промт ноды даёт `prompt.edit_text`: он готовит предложение правки, сам промт пока не меняется.
2. Применение. В той же задаче следом встаёт `change.apply` со своей карточкой: нода, проект, какие строки добавятся и какие уберутся, отметка, что правку можно откатить. Применяется только после одобрения карточки. «Не применяй» пропускает шаг. Позже можно сказать «примени правку промта» или «отмени предложение правки» (`change.reject`): если ожидающих предложений несколько, чат спросит, какое (с нодой и проектом).
3. Откат. «Откати правку промта» находит версию, применённую через этот чат, и ставит `change.rollback` с карточкой. Прежние значения хранятся как версии в change control (`config_versions` в `app/services/change_control/store.py`, таблица только дописывается), поэтому откат возвращает ровно то, что было, а применённые и откатанные версии остаются в истории.

## Как запустить тесты

Тесты гоняются по одному файлу.

SQLite (по умолчанию, без `TEST_DATABASE_URL`)
```
python -m pytest tests/test_<имя>.py -q
```

Postgres. Файлы `tests/*postgres*.py` без `TEST_DATABASE_URL` пропускаются.
```
docker run -d --name vp-test-pg -e POSTGRES_PASSWORD=<пароль> -p 55432:5432 postgres:16
set TEST_DATABASE_URL=postgresql+asyncpg://postgres:<пароль>@127.0.0.1:55432/postgres
python -m pytest tests/test_orch_tenant_postgres.py -q
docker rm -f vp-test-pg
```
Если один файл оставляет данные, которые мешают следующему, для каждого файла лучше поднимать свежую базу.

Веб
```
cd web
npx tsc --noEmit
npm run test:unit
npm run test:e2e:orch
```
Для e2e нужен Chrome (`ORCH_CHROME_PATH`). Порты задаются через `ORCH_WEB_PORT` / `ORCH_MOCK_PORT`, а готовый адрес можно передать через `ORCH_WEB_URL`.

## Что учесть при деплое

1. Сразу после деплоя воркер начинает обслуживать арендаторов, у которых зависла автоматическая работа: проекты в статусе assembled с шагом публикации и включённым auto_mode, ожидающие линии массовой фабрики, батчи в статусе running, истёкшие паузы после ошибок. Платные шаги могут стартовать уже на первом тике. Поэтому до деплоя нужно проверить очереди и балансы, а лишнее остановить.
2. Папки в боковой панели теперь свои у каждого арендатора. У владельца остаётся старый общий список. Старые папки копируются арендатору лениво, при первом обращении.
3. `queue.set_parallel` (изменение числа параллельных проектов) доступен только админу, участники этого действия не видят. Если массовому запуску нужно окно шире текущего, чат показывает две карточки одобрения по очереди: сначала параллельность (`queue.set_parallel`, не выше 10), потом саму очередь. Если окно уже достаточное или стоит на потолке, карточка одна, только очередь.
4. Известное ограничение: кадры старых проектов, которые лежат только в отдельном `project.db` проекта, в общую базу не импортируются.
