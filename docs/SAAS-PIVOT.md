# SaaS-пивот video-pipeline

**Статус:** спецификация, принята к работе. Ветка `saas-pivot`.
**Дата:** 2026-08-23.
**Основание:** решение владельца от 2026-08-23 — продукт делается как SaaS,
не self-hosted и не агентская услуга.

Документ описывает целевую систему и путь к ней. Всё, что здесь названо
«фактом», измерено на живом прогоне проекта #2 (24 кадра, 70 секунд) и взято
из журналов `llm_calls` / `media_calls`, а не оценено.

---

## 1. Что продаём

Пользователь заходит на сайт, в чате описывает нужный ролик, агент ведёт его
по шагам с визуализацией результата на каждом. Перед каждым шагом видна цена
в кредитах. Кредиты покупаются заранее и списываются с баланса.

Ключевая механика — **итерация на дешёвых шагах**. Не понравился кадр:
пользователь правит промт и перерисовывает **только этот кадр** за копейки.
Видео генерируется один раз, в конце, когда раскадровка утверждена.

Это не «сгенерируй ролик кнопкой». Это монтажный стол, где машина делает
черновую работу, а решения принимает человек.

---

## 2. Решения владельца, зафиксированные

| Решение | Значение |
| --- | --- |
| Модель поставки | SaaS. Self-hosted не рассматривается |
| Курс кредита | **1 кредит = 1 USD** |
| Маржа | **×3 к себестоимости** |
| Кто платит за перегенерацию | Пользователь: это его выбор, а не брак системы |
| Кто платит за брак системы | Платформа (см. §5.5) |
| Валюта пополнения | Рубли. Конвертация в доллары **в момент пополнения**, дальше все расчёты в долларах (§5.6) |
| Бесплатный уровень | Всё до первой генерации видео на аккаунте (§5.7) |
| ToS провайдеров на перепродажу | Риск принят владельцем осознанно (§12) |

## 3. Где что живёт: два репозитория, одна касса

Владелец спросил: интегрировать в `llm-gateway` (Chattiq) или делать
отдельное приложение. Ответ: **общий бэк-офис, раздельный фронт-офис**.

### 3.1 Что берём из `llm-gateway` целиком

Разбор кода `llm-gateway/billing` (NestJS 10 + TypeORM + Postgres 16)
показал, что вся скучная и юридически рискованная часть SaaS уже написана и
работает в проде:

| Модуль | Что даёт |
| --- | --- |
| `auth` | JWT, регистрация, верификация почты |
| `users` | `User` с полем `brand`, уникальность по паре `(email, brand)` — мультибренд заложен в схему |
| `payments` | YooKassa, рублёвые платежи |
| `receipts` | Чеки по 422-ФЗ через `lknpd.nalog.ru` (ADR-0029) |
| `transaction` | Проводки `topup / usage / adjustment`, суммы в `numeric(18,8)` USD **и** в копейках |
| `storage` | S3-совместимое хранилище (Cloudflare R2), presigned URL, изоляция префиксом на пользователя |
| `catalog` | Каталог услуг |
| `magic` | Заказы: `MagicOrder` со статусами, очередь, воркеры, SSE-стрим, артефакты, `share_token`, черновики. **Оплата с баланса уже есть**: `paymentMethod='balance'` → заказ сразу `paid` → `enqueue` |
| `deploy` | Caddy, docker-compose, CICD по push в main |

Переписывать это заново — минимум три месяца и юридический риск на приёме
платежей. Не переписываем.

**Модуль `magic` — прямой прецедент.** Это уже маркетплейс генеративных
услуг с оплатой с баланса, очередью, событиями задания и артефактами.
Видео-конвейер становится ещё одной услугой в этом каталоге.

### 3.2 Что делаем отдельно

**Фронт видеостудии — отдельное приложение под отдельным брендом.**

`llm-gateway/dashboard` — React 18 + Vite + Bootstrap + Tailwind, панель
управления ключами и балансом. Видеостудия — Next 15 + React 19 + React Flow
+ Radix: канвас графа, лента кадров, покадровая перегенерация, плеер.
Это разные приложения по природе; сращивание их в один фронт сломает оба.

Поле `brand` в `User` для этого и сохранено (ADR-0019).

### 3.3 Границы

```
                    ┌──────────────────────────────────┐
  Пользователь ───► │  video-studio (Next 15)          │
                    │  чат + канвас + лента кадров     │
                    └───────┬──────────────────┬───────┘
                            │ JWT (SSO)        │ шаги, SSE
                            ▼                  ▼
              ┌─────────────────────┐  ┌────────────────────────┐
              │ llm-gateway/billing │  │ video-pipeline (FastAPI)│
              │ личность, баланс,   │◄─┤ движок генерации:       │
              │ платежи, чеки,      │  │ холд/списание по шагам  │
              │ артефакты в R2      │  │ конвейер, воркеры       │
              └─────────────────────┘  └────────────────────────┘
                            └──────── Postgres 16 ────────┘
```

**Правило границы, уточнённое реализацией 2026-08-24.** Первая редакция
говорила «деньги знает только `billing`, `video-pipeline` не хранит
балансов». На деле §5.3 положила леджер в студию, и там он и построен: холды
привязаны к шагам, промо-проводки — к бесплатному уровню, `cost_usd` — к
журналам вызовов. Переносить это в биллинг значит тянуть туда весь конвейер.

Граница проходит иначе, и так честнее: **рубли, чеки, платёжный провайдер и
личность — биллинг; кредиты, холды и себестоимость — студия.** Между ними
одно направление данных: после успешного платежа биллинг зовёт
`POST /api/billing-hook/topup` и начисляет кредиты. Секрет у этой ручки
отдельный от `JWT_SECRET` — иначе клиент пополнял бы себе баланс собственным
токеном; вызов идемпотентен по `payment_id`, потому что платёжные провайдеры
повторяют вебхуки, а начисленное дважды пополнение никто не заметит до
сверки.

## 4. Идентичность и арендатор

Сегодня в `video-pipeline` арендатора нет вообще: нет ни пользователя, ни
организации, ни `owner_id` у проекта. Авторизация — один общий пароль и токены
в памяти процесса (`app/web/auth_sessions.py`, `_TOKENS: dict`), теряются при
рестарте, и та отключаема флагом `WEB_AUTH_ENABLED`.

### 4.1 Целевое состояние

- Единственный источник личности — `billing`. `video-pipeline` принимает
  подписанный JWT и **не имеет своей формы входа**.
- В каждую таблицу верхнего уровня добавляется `tenant_id UUID NOT NULL`:
  `projects`, `entities`, `frames` (через проект), `artifacts`, `llm_calls`,
  `media_calls`, `hitl_requests`, `node_runs`, `master_prompts`,
  `prompt_versions`, `library_*`, `workflows`.
- Каждый запрос к БД фильтруется по `tenant_id`. Не «не забыть отфильтровать»,
  а **row-level security в Postgres**: политика на таблицу, `SET LOCAL
  app.tenant_id` в начале транзакции. Забыть фильтр физически нельзя.
- Квоты на арендатора: число параллельных проектов, размер хранилища,
  максимум кадров в ролике.

### 4.2 Почему RLS, а не фильтр в коде

В кодовой базе 324 файла и 67 из них ходят в данные проекта. Один
пропущенный `where tenant_id` = утечка чужого ролика. Фильтр в коде — это
требование к разработчику, а весь сегодняшний разбор дефектов (§11
`SHOTS-FIX-2026-08-23.md`) про то, чем кончаются требования, которые некому
проверить. RLS переносит проверку в место, которое нельзя обойти.

## 5. Кредиты

### 5.1 Курс и маржа

```
1 кредит = 1.00 USD цены продажи
цена шага = себестоимость × 3
```

Себестоимость — фактическая сумма `cost_usd` по вызовам шага из
`llm_calls` и `media_calls`. Маржа применяется на этапе котировки, а не
после факта: пользователь видит цену до нажатия.

### 5.2 Дробность: считаем в микрокредитах

При курсе 1 кредит = $1 самая дешёвая операция (одна картинка) стоит
**0.0105 кредита**. Значит кредит обязан быть дробным.

- **Хранение:** целое число микрокредитов, 1 мкр = 10⁻⁶ кредита.
  Никаких float в деньгах.
- **Отображение:** 2 знака после запятой, вниз для баланса, вверх для цены.
- **Совместимость:** `Transaction.amountUsd` в биллинге — `numeric(18,8)`,
  влезает без изменений.

### 5.3 Схема леджера

Дополняет существующие таблицы биллинга, не заменяет их.

```sql
-- Счёт арендатора. Баланс — производная от проводок, но материализован
-- для скорости и сверяется ночной задачей.
create table credit_accounts (
  tenant_id      uuid primary key,
  balance_micro  bigint not null default 0,
  updated_at     timestamptz not null default now()
);

-- Резерв под шаг. Живёт от старта шага до его конца.
create table credit_holds (
  id             uuid primary key,
  tenant_id      uuid not null,
  project_id     bigint not null,
  step_code      text not null,
  node_key       text,
  amount_micro   bigint not null,          -- по оценке p90
  state          text not null,            -- held | settled | released | expired
  expires_at     timestamptz not null,     -- страховка от зависшего шага
  created_at     timestamptz not null default now()
);

-- Проводка. Единственный источник правды по деньгам.
create table credit_entries (
  id             uuid primary key,
  tenant_id      uuid not null,
  hold_id        uuid references credit_holds(id),
  delta_micro    bigint not null,          -- + пополнение, − списание
  kind           text not null,            -- topup | settle | release | refund | adjust | promo
  cost_usd       numeric(18,8),            -- фактическая себестоимость операции
  margin         numeric(6,3),             -- применённая маржа (для аудита)
  ref_table      text,                     -- 'llm_calls' | 'media_calls'
  ref_ids        bigint[],                 -- какие именно вызовы оплачены
  created_at     timestamptz not null default now()
);

create index on credit_entries (tenant_id, created_at desc);
create index on credit_holds (tenant_id, state) where state = 'held';
```

`ref_table` / `ref_ids` смотрят в существующие журналы вызовов. Благодаря
этому по каждой списанной копейке видно, из каких вызовов она сложилась:
маржа считается по продукту, по клиенту и по шагу с первого дня, а не
задним числом.

### 5.4 Жизненный цикл: холд → списание → возврат

1. **Котировка.** Перед шагом считается оценка (см. §6.4). Пользователю
   показывается цена; агент не запускает шаг без явного согласия на дорогих
   шагах (порог — §7.3).
2. **Холд.** Резервируется **p90** оценки, не медиана. Проводка не создаётся,
   баланс уменьшается на сумму холда. Пользователь видит «зарезервировано».
3. **Исполнение.** Шаг пишет вызовы в `llm_calls` / `media_calls` как сейчас.
4. **Списание.** По завершении суммируется фактический `cost_usd` вызовов
   этого шага, умножается на маржу, создаётся `credit_entries(kind='settle')`,
   холд закрывается, **остаток возвращается на баланс той же операцией**.
5. **Отказ.** Шаг упал — холд снимается целиком (`kind='release'`).
   Пользователь не платит ни за одну попытку.
6. **Зависание.** `expires_at` прошёл, шаг не закрылся — холд освобождается
   фоновой задачей, шаг помечается сбойным. Деньги не зависают никогда.

Инвариант, который проверяется тестом: `balance = Σ delta_micro − Σ held`.
Расхождение — авария, а не «поправим потом».

### 5.5 Кто платит за брак

Владелец: «неудачных попыток не будет, всё будет отлажено». По журналам это
почти так, и вот точная цифра.

| Источник | Факт по журналам |
| --- | --- |
| Текстовые вызовы: отказ API, таймаут, исключение | 9 из 223 = **4.0%** |
| Контракт отбил ответ модели | 1 из 223 = **0.4%** |
| Медиа: отказ провайдера | **0** (два `error` в журнале — гашение бэкенда при рестарте) |

Падает дешёвое: 4% приходятся на текст, а текст — $0.87 из $5.53. Остаточный
брак ≈ **$0.02 на ролик**, то есть 0.4% себестоимости. При марже ×3 это
незаметно.

**Политика:** платформа съедает всё, что не является выбором пользователя.
Технически это уже обеспечено пунктом 5 жизненного цикла — холд снимается
целиком. Дополнительно:

- бюджет попыток на шаг (по умолчанию 2), после которого шаг честно
  объявляется несостоявшимся, а не крутится вечно;
- вызовы, оплаченные провайдером, но завершившиеся ошибкой (сегодня такой
  был один, $0.33), пишутся в `credit_entries(kind='adjust')` с нулевым
  `delta_micro` — не списываются с клиента, но видны в отчёте о марже.

### 5.6 Пополнение в рублях, расчёты в долларах

Решение владельца: пользователь платит рублями, конвертация происходит
**один раз — в момент пополнения**, после чего баланс и все списания живут в
долларах.

Это правильная конструкция, и вот почему: себестоимость у нас долларовая
(MiniMax, ElevenLabs), а выручка рублёвая. Если конвертировать при списании,
валютный риск висит на платформе всё время, пока кредиты лежат на балансе.
При конвертации в момент пополнения риск закрывается сразу: клиент купил
доллары по курсу дня, дальше курс никого не касается.

**Механика**

**Решение владельца 2026-08-24: пакетов нет.** Пользователь пополняет баланс
произвольной суммой в рублях. Это упрощает и запуск, и код: номиналы — это
таблица, витрина, отдельный экран и отдельный разговор про «а почему столько».
Пополнение произвольной суммой не требует ни одного из них, а маржа и курс от
номинала не зависят. Номиналы можно ввести позже как подсказки поверх той же
формы — это добавление, а не переделка.

1. Пользователь вводит сумму в рублях.
2. YooKassa проводит платёж, `billing/payments` фиксирует `amount_kopecks`.
3. Курс берётся на момент подтверждения платежа и **записывается в проводку**.
4. На баланс зачисляется `amount_usd = amount_kopecks / 100 / rate`,
   проводка `credit_entries(kind='topup')`.
5. Чек по 422-ФЗ выставляется в рублях на фактически уплаченную сумму —
   это уже работает в `billing/receipts`, менять нечего.

**Курс.** Источник — ЦБ РФ на дату платежа, плюс наценка. Наценка не жадность,
а фактическая стоимость конвертации: карточный эквайринг и трансграничный
перевод к провайдерам съедают порядка 2–4%. Значение наценки — конфигурация,
не константа в коде.

**Что хранить в проводке.** Существующая `Transaction` в биллинге уже несёт
`amountUsd numeric(18,8)`, `amountKopecks bigint` и `meta jsonb` — этого
достаточно. В `meta` кладём:

```json
{ "fx_rate": 94.37, "fx_source": "cbr", "fx_markup": 0.03, "fx_at": "2026-08-23T09:00:00Z" }
```

Курс в проводке обязателен: без него нельзя ни разобрать спор с клиентом, ни
посчитать реальную маржу задним числом.

**Возвраты** — в рублях по курсу исходного пополнения, не текущему. Иначе
на движении курса возврат становится либо подарком, либо обманом.

**Отображение.** Баланс показывается в кредитах (то есть долларах), рядом —
справочный рублёвый эквивалент по текущему курсу с пометкой «примерно».
Цены шагов — только в кредитах: они долларовые по природе.

### 5.7 Бесплатный уровень: всё до первого видео

Решение владельца: бесплатно всё, что идёт до первой генерации видео.

**Экономика подарка.** Полная себестоимость доvideo-части:

| Часть | Себестоимость |
| --- | ---: |
| Текст (план → сценарий → сцены → промты) | $0.87 |
| Герои и предметы | $0.01 |
| 24 картинки | $0.084 |
| **Итого подарок** | **$0.97** |

Это 17% полного ролика. Человек получает готовую раскадровку — сценарий,
24 кадра, контактный лист — и платит только за рендер. Витрина честная:
качество видно до оплаты.

**Граница бесплатного.** Бесплатность действует **до первой оплаченной
генерации видео на аккаунте**. После неё все шаги любого проекта тарифицируются
обычным порядком. Формулировка «до первого видео» относится к аккаунту, а не к
каждому новому проекту: иначе подарок повторяется бесконечно и становится
$0.97 за каждый созданный проект.

**Предохранители — обязательны.** Бесплатная перегенерация картинок стоит
платформе денег, и без потолков это дыра:

| Ограничение | Значение по умолчанию |
| --- | --- |
| Проектов в бесплатном режиме | 1 |
| Кадров в бесплатном проекте | 24 |
| Бесплатных перегенераций картинок | 2 × число кадров (48) |
| Бесплатных перегенераций сценария/раскадровки | 2 |
| Потолок расхода на бесплатный аккаунт | $3.00, дальше требуется пополнение |
| Подтверждение почты | обязательно до старта первого шага |

Все счётчики ведутся в тех же `credit_entries` — проводками с нулевым
`delta_micro` и `kind='promo'`, где `cost_usd` заполнен фактической
себестоимостью. Это даёт отчёт «сколько стоит привлечение» без отдельной
подсистемы.

**Реализовано 2026-08-23** — `app/services/free_tier.py`, врезано в кассу
(`step_billing`): пока подарок действует, шаг идёт без холда, а после него
пишется промо-проводка. Что выяснилось при сборке:

* *Проводке понадобился адрес.* У списания проект и шаг несёт холд, у промо
  холда нет вовсе — она получалась безадресной, и по ней нельзя было ни
  сосчитать бесплатные проекты, ни сказать, во сколько обошёлся клиент.
  Ревизия `0008` добавила `project_id` и `step_code` в `credit_entries`.
* *Потолок проверяется по p90, а не по медиане.* Платформа платит за худший
  исход; считать по среднему значит регулярно проскакивать за потолок ровно
  на разницу.
* *Исчерпанный подарок — не отказ шага.* Наружу это то же самое, что пустой
  баланс: проект ждёт пополнения, статус не трогается. Иначе счётчик неудач
  воркера откатывал бы работу клиента назад за то, что он не заплатил.
* *Подтверждение почты не выполняется.* Токен биллинга несёт `sub`, `email` и
  `brand`, но не `emailVerified` — проверить нечем. Правка на стороне
  биллинга: добавить поле в `auth.service.ts::sign`. До неё требование из
  таблицы выше не обеспечено ничем.
* *Из четырёх предохранителей таблицы реализованы три.* Кадры в бесплатном
  проекте и число бесплатных перегенераций отдельными счётчиками не
  считаются: экономически их закрывает потолок расхода — сто кадров упрутся
  в $3 раньше, чем в лимит кадров. Отдельные счётчики появятся тогда, когда
  понадобится объяснять клиенту, ЧТО именно кончилось, а не только что.

**Что видит пользователь.** «Раскадровка и кадры — бесплатно. Оплата только
за рендер видео: 13.68 кредита за 24 клипа». Момент оплаты наступает ровно
там, где ценность уже доказана.

### 6.2.1 Разрешение по умолчанию дороже, чем считает прайс-лист

**Требует решения владельца.** Весь §6.1–6.2 посчитан на клипе 768P за $0.19.
Система по умолчанию отдаёт 1080P: у проекта `video_resolution` не задан,
`normalize_video_resolution(None)` даёт `1080P`, и тариф выходит $0.33.

| | 768P (в спеке) | 1080P (по умолчанию) |
| --- | ---: | ---: |
| Клип | $0.19 | $0.33 |
| 24 клипа | $4.56 | $7.92 |
| Цена видео, кредитов | **13.68** | **23.76** |
| Ролик целиком | $5.625 → 16.88 кр | $8.985 → **26.96 кр** |

То есть ролик по умолчанию стоил бы на 60% дороже, чем написано в §1 и §6.2.

**Решение владельца 2026-08-24: разрешение выбирается на шаге генерации.**
Не задаётся один раз на проект и не фиксируется в спеке — человек выбирает
перед рендером, видя обе цены. Это лучший из трёх вариантов: 720p дешевле,
1080P красивее, и кто из них важнее — знает только тот, кто платит.

Отсюда требование к интерфейсу: **выбор разрешения обязан быть выбором цены,
а не двух слов.** Показать «720p / 1080p» без цифр значит предложить решение
вслепую, а разница — вдвое. Реализовано: `GET /projects/{id}/steps/video/options`
отдаёт цену каждого варианта, `?resolution=` у сметы отвечает «а если так» и
выбор проекта при этом НЕ меняет (смета — вопрос, а не решение), а `runStep`
с `resolution` сохраняет выбор ДО расчёта холда: иначе человеку показали бы
цену одного разрешения, а списали по другому.

Числа §6.1–6.2 остаются как есть — они посчитаны для 768P, и это теперь одна
из двух цен, а не единственная.

Держится тестом `test_default_resolution_costs_more_than_the_spec_assumes` —
обе цифры лежат рядом, и разъехаться молча они не смогут.

### 6.4 Лестница уточнения оценки

Смета делится надвое, и это принципиально.

- **Детерминированная часть — медиа.** Как только известно число кадров,
  цена считается точно: `N × usd_per_call` из `media_prices.json`, где ключ —
  `провайдер:модель@разрешение:длительность`. Ошибиться нельзя.
- **Стохастическая часть — текст.** Зависит от числа вызовов; берётся медиана
  и p90 по историческим данным того же шага.

| Момент | Что известно | Точность оценки |
| --- | --- | --- |
| Пользователь описал тему | ничего | вилка ×2 |
| После сценария | символы → секунды → кадры (14 симв/с, кадр ≈ 2.9 с) | медиа точно, текст ±30% |
| Перед конкретным шагом | всё | точно |
| **Перед видео** | кадры × тариф | **точно, до цента** |

Самый дорогой шаг оказался самым предсказуемым: видео тарифицируется за
вызов, а не за токены.

**Реализовано** — `app/services/quote.py` (Этап 0, §11). Две вещи выяснились
при сборке и стоят того, чтобы их не переоткрывать:

* *Смета шага — сумма обеих частей, а не выбор между ними.* У шага
  «Картинки» есть и точная медийная строка (24 PNG по прайсу), и
  стохастическая текстовая — проверка кадра зрением. Посчитав только
  первую, занижаешь холд на треть.
* *Одного прогона в истории мало, и он запросто отладочный.* В проекте #2
  раскадровка перезапускалась десяток раз, и её «медиана» вчетверо выше
  чистого прогона. Поэтому при тонкой истории показывается справочная
  величина §6.1, а резервируется худшее наблюдение: излишек холда
  возвращается, нехватка останавливает шаг на середине.

> уйдёт за десятки тысяч роликов в месяц.

переплату за пакет):

| Объём | Символов/мес | Оптимум | $/мес |
| --- | ---: | --- | ---: |
| 500 роликов | 475k | Creator годовой ($18.33) + PAYG $25.50 | **≈ $43.8** |

video → audio → assemble`), поэтому в бесплатный уровень (§5.7) она не

## 7. Перегенерация как продукт

### 7.1 Цена перегенерации — это радиус поражения, а не шаг

Разброс двадцатикратный: правка одного кадра стоит 0.68 кредита, а правка
сценария — 16.59. Пользователь, который «пошёл поменять промпт», должен
видеть, что именно сгорит, **до** нажатия.

Радиус считается по графу зависимостей шагов, который в системе уже есть.

### 7.2 Точечная перегенерация уже реализована

`app/services/hitl_apply.py`:

- `HITLDecision.regenerate` / `edit_prompt` на карточке картинок → кадр
  откатывается в `FrameStatus.image_prompt_ready`;
- то же на карточке видео → кадр откатывается в `animation_prompt_ready`.

Шаг доделывает **только откатившиеся кадры**. То есть ядро продукта —
«не понравился кадр, поменял промт, перерисовал один» — работает на уровне
данных. Не хватает чата поверх.

### 7.3 Правила интерфейса, вытекающие из цены

1. **Две кнопки, визуально разные.** «Перерисовать кадр — 0.01 кр» и
   «Переделать раскадровку — 14.67 кр» не должны выглядеть одинаково.
2. **Каскад — только через подтверждение** со списком того, что сгорает:
   «будут заново созданы 24 промта, 24 картинки и 24 клипа».
3. **Порог обязательного подтверждения — 1 кредит.** Всё дешевле выполняется
   сразу, дороже — спрашивает.
4. **Явная остановка перед видео.** Агент говорит: «раскадровка утверждена,
   24 клипа = 13.68 кредита, после этого правки станут дорогими».
5. **Пакет черновых клипов.** 512P втрое дешевле 1080P (0.30 против 0.99).
   Продавать как «черновой просмотр движения» перед финальным рендером.

### 9.1.1 Изоляция за пределами базы — сделано 2026-08-23

Row-level security закрывает базу и не закрывает больше ничего. Два места,
где в SaaS изоляции не было вовсе, и оба нашлись при разборе §9.2.

**Файлы отдавались по пути.** `GET /api/files?path=…` проверял ровно одно:
что путь лежит под `data_dir`. Это защита от выхода за пределы каталога и
ничего не говорит о том, чей это файл, а `data_dir` в SaaS общий на всех:
клиент с законным токеном, узнав чужой слаг, забирал чужой ролик целиком —
не обходя политику, а идя мимо неё. Закрыто `app/services/file_scope.py`:
путь раскладывается до слага проекта по объявленной в `Project.data_dir`
раскладке, слаг ищется в базе, и чужой не находится, потому что его прячет
RLS. Ответ — 404, а не 403: подтвердить существование чужого проекта значит
отдать сведения о нём вместо самого файла.

**Половина API оказалась инструментами владельца.** `/api/fleet` запускает
PowerShell на машинах парка, `/api/db` листает базу напрямую, `/api/text-llm`
и `/api/grsai` ходят к провайдерам мимо кассы, `/api/prompts` правит промты
платформы сразу для всех. Всё это писалось под одного хозяина за своей
машиной и открывалось любому арендатору с валидным токеном.

Закрыто **списком разрешённого**, а не запрещённого
(`identity.TENANT_ALLOWED_PREFIXES`). Список запрещённого означал бы, что
каждый новый роутер открыт, пока кто-нибудь не вспомнит его закрыть, — тот
самый способ терять изоляцию, из-за которого в §4.2 выбран RLS вместо
фильтра в коде. Добавить путь в список значит утверждать: он отдаёт только
данные этого клиента и тратит только его деньги.

В режиме владельца обе проверки выключены целиком: `data_dir` принадлежит
одному человеку, и панель парка — его рабочий инструмент.

`project.data_dir`. В биллинге уже есть `StorageService` на S3/R2 с

контракт, а не пишем свой.

Работа: ввести абстракцию хранилища, заменить прямые `Path` на неё,
перенести отдачу файлов на presigned URL.

**Сделано 2026-08-23.** Абстракция и публикация результата — есть; перевод
всего конвейера на неё — нет, и не нужен: ffmpeg монтирует с диска, а не из
сети, провайдер отдаёт байты в файл, проверка кадра открывает его же.

| `app/services/storage/local.py` | диск узла — рабочий режим владельца |
| `app/services/storage/s3.py` | S3-совместимое (R2 и прочие) через boto3 |
| `app/services/artifact_storage.py` | публикация артефактов и выбор ссылки |
| `migrations/0009` | `artifacts.storage_key` |

Контракт зеркалит `llm-gateway/.../storage.service.ts` — тот же продукт, та же
касса, расходиться им незачем. Оттуда же три решения, за которые там уже
заплачено практикой: изоляция префиксом ключа, «выключено — значит работает
локально, а не падает», жёсткая санитизация пути как poka-yoke.

Четыре вещи, которые стоит знать:

* **Локальный файл никуда не девается.** Ключ добавлен рядом с путём, а не
  вместо него. Отобрать у конвейера файл на диске ради чистоты значит сломать
  монтаж.
* **Публикация в одном месте.** После успешного шага, а не из двадцати шести
  точек создания артефактов: забыть в одной значило бы потерять ровно один
  вид результата и узнать об этом по жалобе.
* **Ошибка публикации не роняет шаг.** Ролик уже сгенерирован и оплачен;
  уронить шаг из-за недоступного бакета значит списать деньги и не отдать
  результат. Ключ остаётся пустым, отдача идёт с диска, следующий шаг
  попробует снова.
* **Отдача опубликованного идёт мимо приложения** — перенаправлением на
  подписанную ссылку (307, не 302: метод обязан сохраниться, а ссылка живёт
  по сроку и кэшировать её нельзя). Ролик это десятки мегабайт, и каждый
  просмотр через FastAPI занимал бы воркер на всё время скачивания.

**Живого бакета код не видел.** Ключи, санитизация и переключение отдачи
проверены тестами; подпись SigV4 и поведение конкретного провайдера — нет.
Это первое, что нужно сделать, когда появится бакет: положить файл, забрать
по ссылке, проверить `force_path_style` — ошибка в нём выглядит как «бакет не
найден» на совершенно рабочем бакете.

### 9.3 Excel — только выгрузка

**Это главный архитектурный долг.** 67 файлов из 324 знают про
`project.xlsx`, 27 работают с `openpyxl` напрямую.

Сегодня на этом обожглись буквально: монтаж брал тайминг из строки R15 листа
«план», где ровно 13 колонок — по одной на ячейку закадра. Развёртка сцены в
шоты живёт только в базе, и монтаж молча выбросил 11 клипов из 24, а хвост
ролика 32 секунды стоял на стоп-кадре. Починено переводом монтажа на
`Frame.start_ts/end_ts` (`docs/SHOTS-FIX-2026-08-23.md` §15) — это первый шаг
ровно этой миграции.

В SaaS Excel нет вообще: некому его открыть, некому «сохранить и закрыть».

Работа: пройти оставшиеся точки чтения xlsx и перевести на БД; оставить
только экспорт по кнопке. Порядок — от шагов, ближайших к деньгам
(монтаж — сделано, картинки, промты), к вспомогательным.

**Сделано 2026-08-23, и оказалось дешевле, чем считалось.** Развязка не
потребовала переписывать шестьдесят семь файлов, потому что шаги, ближайшие
к деньгам, УЖЕ спрашивают сначала базу: `generate_images._load_refs_for_frame`
идёт в книгу, только если рефов в базе нет. То есть чтение развязано,
осталась запись — а она в SaaS не нужна вовсе.

Введена настройка `XLSX_WRITE`: по умолчанию включена в режиме владельца и
выключена в SaaS. Выключается **запись**, чтение остаётся — данные,
заведённые в Excel до перехода, не пропадают.

Выключение стоит в двух местах: на `ensure_initialized` (файл не создаётся
вовсе — пустая книга на диске выглядит испорченной и однажды приведёт
кого-нибудь к мысли её починить) и на самом `_save` как последний рубеж:
точек записи шестьдесят семь файлов, закрывать каждую значит закрыть
шестьдесят шесть и забыть одну.

**Что это даёт прямо сейчас.** На каждом из двадцати четырёх кадров openpyxl
перечитывал и переписывал книгу целиком ради файла, который в SaaS никто не
откроет. Теперь не перечитывает.

**Что осталось.** Переписывание оставшихся точек на БД — по-прежнему самый
длинный этап, но теперь он ничего не блокирует и может идти по одной точке
за раз. Экспорт по кнопке (`GET /projects/{id}/xlsx`) остаётся как был.

### 9.4 Промт-библиотека в БД

Сейчас `.gitignore: prompts/*` — библиотека намеренно вне git. Следствие:
на чистом клоне 56 тестов падают на отсутствии данных, а не кода
(`.claude/baselines/pytest-failures.txt`).

В SaaS промты обязаны быть версионируемыми данными с переопределением на
арендатора. Таблицы `master_prompts` и `prompt_versions` уже есть — задел
наполовину сделан.

Работа: загрузчик библиотеки в БД, разрешение «системный → бренд →
арендатор → проект», UI редактирования промтов (он же — то место, куда
пользователь идёт «менять промпт на более лучший»).

**Сделано 2026-08-24** — `app/services/prompt_store.py`, ревизия `0010`.
Таблица `prompt_library` даёт четыре уровня переопределения, разрешение идёт
от частного к общему, первый найденный побеждает. Файл на диске остался
последним звеном цепочки: он источник правды режима владельца и он же
наполняет системный уровень загрузчиком при первом старте.

Три решения:

* *Уровень выбирает область, а не вызывающий.* «Сохранить как системный,
  будучи арендатором» — не настройка, а ошибка: один клиент поменял бы промт
  всем остальным.
* *Загрузка с диска не затирает правленое в базе.* Файл мог остаться от
  прошлой версии, а промт в базе — это работа человека, и терять её молча
  нельзя.
* *Кэш процесса, а не запрос на каждое чтение.* `read_prompt` синхронна и
  зовётся из глубины шагов; переписать её на `async` значит тронуть половину
  конвейера ради десятка килобайт, которые между шагами не меняются.
  Плата — правка промта доедет до соседних узлов при их следующем старте;
  когда правки станут частыми, здесь понадобится инвалидация через шину, и
  это будет видно по жалобе «поправил, а не применилось», а не молча.

**Чего нет:** UI редактирования промтов арендатором. Ручки библиотеки
(`/api/prompts`, `/api/prompt-files`) — операторские, в SaaS закрыты списком
разрешённого, и открывать их клиенту нельзя: они правят промты платформы для
всех сразу. Клиентскому редактору нужен свой роутер, пишущий через
`prompt_store.save` в область арендатора.

Это капитал проекта, его не переписывать:

- **Сквозной конвейер.** Тема → скелет → сцены → шоты → промты → 24 кадра →

- **Расчёт присутствия и непрерывности кодом** (`presence.py`,
  `continuity.py`) — то, чего нельзя добиться промтом.
- **Гейт качества** — ruff, mypy в нуле, храповик падений тестов.
- **Точечная перегенерация** (`hitl_apply.py`) — ядро продуктовой петли.

### Этап 1. Postgres, арендатор, леджер — сделано 2026-08-23

**Порядок исправлен.** В первой редакции Этап 1 требовал «`tenant_id` в
схему + RLS», а переезд на Postgres стоял Этапом 3. Это невыполнимо: RLS —
механизм Postgres, в SQLite его нет вовсе. Оставался выбор между двумя
плохими вариантами — фильтр `where tenant_id` в коде, против которого прямо
возражает §4.2, или отложенная изоляция при уже работающих деньгах. Плюс
схема леджера §5.3 написана на диалекте Postgres, то есть на SQLite её
пришлось бы писать дважды. Переезд идёт первым, до денег.

| Модуль | Что делает |
| --- | --- |
| `app/db.py` | движок по диалекту; `SET LOCAL app.tenant_id` в транзакции |
| `app/services/tenant.py` | арендатор в ContextVar; запрет многоарендности без RLS |
| `app/services/tenant_tables.py` | один список изолируемых таблиц на всю систему |
| `app/services/db_busy.py` | «база занята» на обоих диалектах |
| `app/services/db_json.py` | `json_extract` ↔ `->>` |
| `app/services/rls_check.py` | проверка, что изоляция действительно в силе |
| `app/services/credit_ledger.py` | холд → списание → возврат, инвариант баланса |
| `app/services/step_billing.py` | касса вокруг шага; в режиме владельца выключена |
| `migrations/0005`, `0006` | `tenant_id` + таблицы кассы; политики RLS |

Что выяснилось при сборке — в §11.1.

- **Проверено на живом Postgres** (postgres:16, роль `app` — обычная, не
  суперпользователь). Семь тестов `tests/test_rls_postgres.py` зелёные;
  контрольный прогон тех же тестов под суперпользователем валит ровно
  четыре — видимость чужой строки, запись в чужого арендатора, режим
  владельца и проверку роли. Это и есть доказательство, что изоляцию держит
  политика, а не фильтр в коде.
- **Результат:** можно продавать роликами вручную отобранным клиентам.

### 11.1. Три вещи, которые обошлись бы дорого

**`ENABLE ROW LEVEL SECURITY` не действует на владельца таблиц.** А
приложение подключается ровно владельцем. Политики были бы созданы, видны в
`\d+` — и не применялись бы ни к одному запросу. Нужен `FORCE`. Обойти RLS
всё равно может суперпользователь и роль с `BYPASSRLS`, поэтому проверка
роли вынесена в `rls_check` и зовётся на старте: не подняться лучше, чем
подняться без изоляции.

**Снятие резерва — не проводка.** Холд ничего не списывает, он лишь
запрещает потратить те же деньги дважды. Если бы возврат создавал проводку
`+amount`, сумма дельт выросла бы, а сумма холдов упала — доступный остаток
скакнул бы на два резерва вместо одного. Запись `kind='release'` пишется с
нулевой дельтой, как след в журнале.

**Три ревизии из четырёх были написаны на SQLite-only SQL** — `PRAGMA
table_info`, `sqlite_master`. Прогон миграций это первое, что делает новая
инсталляция: на Postgres она не поднялась бы вовсе. Переведены на
`sa.inspect`.

### Этап 1.5. Касса врезана в исполнение шага — сделано 2026-08-23

Котировка и леджер были написаны в Этапе 0–1, но не соединены с конвейером:
`quote.py` и `step_billing.py` не звал никто. Теперь врезка стоит в
`advance_project_job` — единственной точке, через которую проходит любое
исполнение шага: и такт воркера, и ручной запуск из канваса, и повтор после
HITL. Оборачивать сами обработчики значило бы обернуть двадцать с лишним
штук и не забыть ни одного.

| Что | Где |
| --- | --- |
| резерв до шага, списание после, возврат при падении | `app/services/advance_runner.py` |
| объём шага (кадры / символы) касса выясняет сама | `step_billing.step_volume` |
| `статус → код шага` | `node_registry.step_code_of_running_status` |
| цена до нажатия и радиус каскада | `GET /api/projects/{id}/steps/{code}/quote[?cascade=1]` |
| остаток, резервы, проводки | `GET /api/billing/balance` |

Два решения, которые стоит знать:

* **Объём шага не спрашивают у вызывающего.** «Видео» тарифицируется по
  кадрам, «Озвучка» — по символам, «План» — никак. Требовать это знание от
  каждого вызывающего значит недосчитать холд у всех, забыв в одном месте.
* **Нехватка кредитов — не падение шага.** Счётчик неудач воркера
  откатывает проект на предыдущий шаг после нескольких падений подряд. Если
  бы пустой баланс приходил исключением, он разбирал бы работу клиента по
  кусочку каждые несколько минут. Такт возвращается без изменения статуса,
  проект ждёт пополнения, жалоба в журнал пишется раз в пять минут.

Чего в этой части ещё нет: карточки «пополните баланс» — сегодня ожидание
пополнения выглядит для клиента как остановившийся проект. Это Этап 3.

### Этап 2. Личность — приёмная сторона сделана 2026-08-23

| Модуль | Что делает |
| --- | --- |
| `app/services/billing_jwt.py` | разбор и проверка JWT биллинга (HS256, `sub`/`email`/`brand`) |
| `app/web/identity.py` | ASGI-middleware: закрывает `/api/*` и `/ws/*`, кладёт арендатора в контекст |
| `app/services/tenant_provisioning.py` | счёт при первом входе, стартовый подарок ровно один раз |
| `app/web/routers/me.py` | `/api/me` — личность, баланс, момент заведения арендатора |

`tenant_id` — это `User.id` биллинга без таблицы соответствия: там
`@PrimaryGeneratedColumn("uuid")`, здесь `sa.Uuid`. Одна личность — один
арендатор.

Своя форма входа отвечает 410, как только задан `BILLING_JWT_SECRET`. Файлы
`auth.py` / `auth_sessions.py` не удалены: пароль оттуда держит живую панель
флота на машине владельца — единственный интерфейс, который у системы есть до
этапа 3. Уходят вместе с панелью.

- **Осталось:** сторона биллинга — завести бренд видеостудии и выпускать
  токен на её домен.
- **Результат:** живые деньги через существующую кассу.

### 11.2. Что показал живой прогон

Три вещи, которых не видно на SQLite и в тестах без сети.

**Арендатор доезжал не до всех запросов.** `SET LOCAL` ставился в одном месте
— в `session_scope`. Мимо неё ходят шестнадцать роутеров через
`deps.get_session` и двадцать пять прямых `SessionLocal()` в шагах конвейера.
Под RLS настройка у них осталась бы пустой, а политика при пустой настройке
показывает строки без арендатора и только их: шаг отработал, ничего не нашёл,
ничего не сказал. Привязка перенесена на событие `after_begin` сессии —
транзакция физически не может начаться, не сообщив, чья она.

**Слой личности снаружи CORS ломает фронт целиком.** `add_middleware`
вставляет слой в начало списка, поэтому добавленный последним оказывается
снаружи. Браузерный preflight (`OPTIONS`) заголовка `Authorization` не несёт —
снаружи он получал 401 без единого CORS-заголовка, и кросс-доменный фронт не
работал бы вовсе, ещё не успев отправить исправный токен. Проверяется тестом.

**Воркер конвейера не подхватывал ни одного проекта клиента.** Петля
сканировала `projects` по статусу, не назначив арендатора, — под RLS это
ровно проекты владельца и ничего больше. Фильтром не чинится: сканирование
по природе межарендное, а RLS запрещает межарендное чтение, в том и смысл.
**Закрыто маршрутной таблицей** — см. §11.3.

### 11.3. Маршрутная таблица: как воркер находит работу

Сделано 2026-08-23, ревизия `0007`.

`project_routes` хранит **маршрутные факты и только их**: номер проекта, его
арендатор, его статус. Ни тем, ни текстов, ни промтов, ни цен — всё
содержимое остаётся в `projects` под обычной политикой. Воркер читает
маршруты без арендатора, узнаёт, у кого есть работа, и делает её уже под
каждым из них через `tenant_scope`.

**Политика у таблицы обратная обычной.** У всех остальных незаданный
арендатор означает «видно только ничьё»: забытая привязка не должна
становиться утечкой. Здесь сессия без арендатора видит все строки, потому что
режим без арендатора и есть служебный режим воркера — иначе он не найдёт
работу вовсе. Сессия с арендатором видит только свои строки: перечислить
чужие проекты клиент не может. Цена асимметрии ограничена тем, что
перечислять в таблице нечего, кроме номеров и статусов. Проверяется тестом
`test_tenant_cannot_enumerate_foreign_routes`, который краснеет под
суперпользователем вместе с остальными.

**Синхронность держит триггер, а не приложение.** Статус проекта меняют
десятки мест, часть — массовыми `UPDATE` мимо ORM. Требование «не забыть
обновить маршрут» разошлось бы с реальностью на первой же забытой строке, и
разошлось бы молча: воркер перестал бы видеть чей-то проект. Тест
зеркалирования поэтому ходит сырым SQL — тем самым путём, который забывают.

**Списка рабочих статусов в SQL нет.** Он объявлен один раз в
`node_registry.WORKER_ACTIVE_STATUSES` и передаётся в запрос параметром.
Вторая копия в триггере разошлась бы с первой так же молча — воркер перестал
бы видеть целый класс шагов, ничего при этом не сломав.

| Модуль | Что делает |
| --- | --- |
| `app/models.py::ProjectRoute` | схема маршрута |
| `migrations/versions/0007` | таблица, триггер, обратная политика |
| `app/services/work_routing.py` | «у кого есть работа» — единственный межарендный запрос |
| `app/main.py::_run_worker_loop` | тик разбит на «кому служим» и «служим» |

**Что осталось от этого узла.** Обход линейный: тик проходит по всем
арендаторам с работой подряд. На сотнях арендаторов это нормально, на
десятках тысяч — нет, и тогда маршрутную таблицу пора превращать в очередь с
захватом (`work_leases` уже даёт примитив атомарного захвата). Менять это
раньше, чем появятся клиенты, незачем.

### Этап 3.1. Агент и чат — серверная половина сделана 2026-08-23

| Модуль | Что делает |
| --- | --- |
| `app/services/studio_agent/tools.py` | восемь инструментов §8.3 — тонкие обёртки над существующими шагами |
| `app/services/studio_agent/loop.py` | петля «модель просит инструмент → выполняем → она объясняет» |
| `app/web/routers/studio_chat.py` | `POST /api/chat` (SSE) и `GET /api/chat/tools` |
| `web/src/lib/chat-api.ts` | чтение SSE через `fetch` |
| `web/src/components/studio/chat-panel.tsx` | лента разговора с карточками инструментов |

**Отступление от §8.1, названное вслух.** AI SDK и AI Elements не взяты.
`useChat` рассчитан на протокол потока данных провайдера, а у нас поток
серверный: события петли, а не токены модели. Реализовать их протокол на
сервере можно, но это контракт, который придётся сопровождать, ради нуля
сегодняшней пользы. Чтение SSE написано своё — шестьдесят строк. AI Elements
можно взять позже отдельно, чисто ради вида: это копируемые компоненты, а не
зависимость.

**Почему не нативный tool-calling.** У текстового клиента проекта параметра
`tools` нет, а провайдер, на котором держится 82% себестоимости, не
поддерживает даже structured outputs. Строить разговор на функции, которой у
половины поставщиков нет, значит привязаться к одному ровно там, где §12
требует заранее проверенной замены. Контракт тот же, что у всего конвейера:
модель отвечает JSON, разбирает канонический экстрактор (он же вытаскивает
объект из-под `<think>`, который часть моделей пишет прямо в content).

**Как именно исполнено правило §8.2.** Инструмент `runStep` НЕ передаёт
`explicit_ui_start`. Этот флаг — право оператора за своим канвасом: он
снимает очередь, убивает чужой идущий шаг и стартует что угодно поверх.
Агенту такого права не дано; вместо него стоит проверка достижимости по тому
же prerequisite-статусу, по которому рисуется меню шагов. Проект на
`frames_ready` не прыгнет в монтаж, как бы убедительно модель ни объяснила,
что так быстрее.

**Порог подтверждения живёт в инструменте, а не в интерфейсе.** Интерфейсов
будет несколько — чат, канвас, однажды мобильный, — а цена одна. Проверка в
интерфейсе означала бы, что каждый следующий обязан вспомнить про неё.

**Петля конечна, и предел — про деньги.** Каждый виток это платный вызов
модели; зациклившаяся на `showStoryboard` потратит баланс, ничего не сделав.
Восемь витков хватает на самый длинный осмысленный сценарий, а предел ещё и
объясняется человеку вслух — молчаливый обрыв он прочтёт как поломку.

**Чего в этой части нет.** Живой модели агент ещё не видел: все проверки
идут на подменённой. Карточки в ленте показывают цену и число кадров, но не
показывают сами кадры — контактный лист лежит в канвасе, свести их предстоит.

**Не забыть при переезде на Postgres.** Пути на диске всё ещё привязаны к
файлу базы: `settings.sqlite_path.parent` служит каталогом для замка

нужен отдельный `data_dir`. Пока безвредно (файл всё равно лежит рядом), но
на арендаторе с объектным хранилищем сломается тихо.

### Принятый риск: ToS провайдеров

Владелец 2026-08-23 принял риск осознанно, проверка ToS перед запуском не
проводится. Документ фиксирует, в чём именно экспозиция, чтобы решение
осталось решением, а не забытым допущением.

**По ElevenLabs вопрос при поиске тарифа закрылся сам, и в нашу пользу.**
Продажа сгенерированного аудио конечным клиентам разрешена на **любом
платном плане**: «All paid plans include a commercial license, provided
you're not using Beta Services» (docs/help-center), права на вывод остаются
за нами (ToS ред. 31.03.2026, §4(c)(ii)). Два ограничения, которые нас не
задевают, но которые нельзя нарушить по невнимательности:

* **Free-план коммерческого использования не даёт** и требует атрибуции
  «elevenlabs.io». То есть на бесплатном уровне (§5.7) озвучки быть не может
  — и её там нет, она идёт после видео.
* Запрещено «Making Available» — встраивание самого сервиса TTS в продукт
  для конечных пользователей — на планах Free/Starter/Creator/Pro; это
  открывается со Scale (OEM Terms). Мы продаём **готовый ролик**, а не доступ
  к синтезу, поэтому под запрет не попадаем. Если когда-нибудь захотим дать
  клиенту прямой доступ к генерации голоса — понадобится Scale.

**Остаётся риск по MiniMax** — картинки и видео, то есть 82% себестоимости.
Именно к нему относятся смягчения ниже.

Ставка не в штрафе — её в таких ToS обычно нет. Ставка в **блокировке
аккаунта без предупреждения**, и бьёт она по времени: в момент блокировки
встают заказы всех клиентов сразу, деньги за них уже приняты, а перевод на
другого провайдера требует перекалибровки промтов (у MiniMax свои лимиты —
1500 символов на промт картинки, одна character-ссылка на кадр; на другом
провайдере эти ограничения другие).

**Смягчение, которое стоит дёшево и не требует пересмотра решения:**

1. Резервный провайдер на каждый вид генерации, проверенный заранее, а не в
   момент аварии. У `media_route` уже есть выбор провайдера по модели, а
   `img_pr_budget` считает лимит промта по фактическому генератору — то есть
   переключение архитектурно возможно уже сейчас.
2. Не держать на балансе у провайдера больше недельного расхода.
3. Мониторинг ответов 4xx с кодами блокировки — тревога владельцу, а не
   молчаливая остановка очереди.

### Решено владельцем 2026-08-24

1. **Пакетов пополнения нет** — баланс пополняется произвольной суммой
   (§5.6). Номиналы можно добавить позже подсказками поверх той же формы.
2. **Бренд — «Мультик».** Значение поля `brand` в `User` биллинга и
   `STUDIO_BRAND` студии: `multik`. Латиницей намеренно — строка уходит в
   уникальность `(email, brand)`, в URL и в конфигурацию Caddy, а кириллица
   там переживёт не каждый слой. Отображаемое имя — «Мультик».
3. **Разрешение выбирается на шаге генерации** (§6.2.1), а не задаётся на
   проект.
