# SaaS-пивот video-pipeline

**Статус:** спецификация, принята к работе. Ветка `saas-pivot`.
**Дата:** 2026-08-23.
**Основание:** решение владельца от 2026-08-23 — продукт делается как SaaS,
не self-hosted и не агентская услуга.

Документ описывает целевую систему и путь к ней. Всё, что здесь названо
«фактом», измерено на живом прогоне проекта #2 (24 кадра, 70 секунд) и взято
из журналов `llm_calls` / `media_calls`, а не оценено.

---

## 1. Что продаём

Пользователь заходит на сайт, в чате описывает нужный ролик, агент ведёт его
по шагам с визуализацией результата на каждом. Перед каждым шагом видна цена
в кредитах. Кредиты покупаются заранее и списываются с баланса.

Ключевая механика — **итерация на дешёвых шагах**. Не понравился кадр:
пользователь правит промт и перерисовывает **только этот кадр** за копейки.
Видео генерируется один раз, в конце, когда раскадровка утверждена.

Это не «сгенерируй ролик кнопкой». Это монтажный стол, где машина делает
черновую работу, а решения принимает человек.

---

## 2. Решения владельца, зафиксированные

| Решение | Значение |
| --- | --- |
| Модель поставки | SaaS. Self-hosted не рассматривается |
| Курс кредита | **1 кредит = 1 USD** |
| Маржа | **×3 к себестоимости** |
| Кто платит за перегенерацию | Пользователь: это его выбор, а не брак системы |
| Кто платит за брак системы | Платформа (см. §5.5) |
| Валюта пополнения | Рубли. Конвертация в доллары **в момент пополнения**, дальше все расчёты в долларах (§5.6) |
| Бесплатный уровень | Всё до первой генерации видео на аккаунте (§5.7) |
| ToS провайдеров на перепродажу | Риск принят владельцем осознанно (§12) |

## 3. Где что живёт: два репозитория, одна касса

Владелец спросил: интегрировать в `llm-gateway` (Chattiq) или делать
отдельное приложение. Ответ: **общий бэк-офис, раздельный фронт-офис**.

### 3.1 Что берём из `llm-gateway` целиком

Разбор кода `llm-gateway/billing` (NestJS 10 + TypeORM + Postgres 16)
показал, что вся скучная и юридически рискованная часть SaaS уже написана и
работает в проде:

| Модуль | Что даёт |
| --- | --- |
| `auth` | JWT, регистрация, верификация почты |
| `users` | `User` с полем `brand`, уникальность по паре `(email, brand)` — мультибренд заложен в схему |
| `payments` | YooKassa, рублёвые платежи |
| `receipts` | Чеки по 422-ФЗ через `lknpd.nalog.ru` (ADR-0029) |
| `transaction` | Проводки `topup / usage / adjustment`, суммы в `numeric(18,8)` USD **и** в копейках |
| `storage` | S3-совместимое хранилище (Cloudflare R2), presigned URL, изоляция префиксом на пользователя |
| `catalog` | Каталог услуг |
| `magic` | Заказы: `MagicOrder` со статусами, очередь, воркеры, SSE-стрим, артефакты, `share_token`, черновики. **Оплата с баланса уже есть**: `paymentMethod='balance'` → заказ сразу `paid` → `enqueue` |
| `deploy` | Caddy, docker-compose, CICD по push в main |

Переписывать это заново — минимум три месяца и юридический риск на приёме
платежей. Не переписываем.

**Модуль `magic` — прямой прецедент.** Это уже маркетплейс генеративных
услуг с оплатой с баланса, очередью, событиями задания и артефактами.
Видео-конвейер становится ещё одной услугой в этом каталоге.

### 3.2 Что делаем отдельно

**Фронт видеостудии — отдельное приложение под отдельным брендом.**

`llm-gateway/dashboard` — React 18 + Vite + Bootstrap + Tailwind, панель
управления ключами и балансом. Видеостудия — Next 15 + React 19 + React Flow
+ Radix: канвас графа, лента кадров, покадровая перегенерация, плеер.
Это разные приложения по природе; сращивание их в один фронт сломает оба.

Поле `brand` в `User` для этого и сохранено (ADR-0019).

### 3.3 Границы

```
                    ┌──────────────────────────────────┐
  Пользователь ───► │  video-studio (Next 15)          │
                    │  чат + канвас + лента кадров     │
                    └───────┬──────────────────┬───────┘
                            │ JWT (SSO)        │ шаги, SSE
                            ▼                  ▼
              ┌─────────────────────┐  ┌────────────────────────┐
              │ llm-gateway/billing │  │ video-pipeline (FastAPI)│
              │ личность, баланс,   │◄─┤ движок генерации:       │
              │ платежи, чеки,      │  │ холд/списание по шагам  │
              │ артефакты в R2      │  │ конвейер, воркеры       │
              └─────────────────────┘  └────────────────────────┘
                            └──────── Postgres 16 ────────┘
```

**Правило границы:** деньги и личность знает только `billing`.
`video-pipeline` не хранит балансов и не считает цен в рублях — он сообщает
биллингу «шаг X проекта Y стоил $Z» и «зарезервируй под шаг X сумму H».

## 4. Идентичность и арендатор

Сегодня в `video-pipeline` арендатора нет вообще: нет ни пользователя, ни
организации, ни `owner_id` у проекта. Авторизация — один общий пароль и токены
в памяти процесса (`app/web/auth_sessions.py`, `_TOKENS: dict`), теряются при
рестарте, и та отключаема флагом `WEB_AUTH_ENABLED`.

### 4.1 Целевое состояние

- Единственный источник личности — `billing`. `video-pipeline` принимает
  подписанный JWT и **не имеет своей формы входа**.
- В каждую таблицу верхнего уровня добавляется `tenant_id UUID NOT NULL`:
  `projects`, `entities`, `frames` (через проект), `artifacts`, `llm_calls`,
  `media_calls`, `hitl_requests`, `node_runs`, `master_prompts`,
  `prompt_versions`, `library_*`, `workflows`.
- Каждый запрос к БД фильтруется по `tenant_id`. Не «не забыть отфильтровать»,
  а **row-level security в Postgres**: политика на таблицу, `SET LOCAL
  app.tenant_id` в начале транзакции. Забыть фильтр физически нельзя.
- Квоты на арендатора: число параллельных проектов, размер хранилища,
  максимум кадров в ролике.

### 4.2 Почему RLS, а не фильтр в коде

В кодовой базе 324 файла и 67 из них ходят в данные проекта. Один
пропущенный `where tenant_id` = утечка чужого ролика. Фильтр в коде — это
требование к разработчику, а весь сегодняшний разбор дефектов (§11
`SHOTS-FIX-2026-08-23.md`) про то, чем кончаются требования, которые некому
проверить. RLS переносит проверку в место, которое нельзя обойти.

## 5. Кредиты

### 5.1 Курс и маржа

```
1 кредит = 1.00 USD цены продажи
цена шага = себестоимость × 3
```

Себестоимость — фактическая сумма `cost_usd` по вызовам шага из
`llm_calls` и `media_calls`. Маржа применяется на этапе котировки, а не
после факта: пользователь видит цену до нажатия.

### 5.2 Дробность: считаем в микрокредитах

При курсе 1 кредит = $1 самая дешёвая операция (одна картинка) стоит
**0.0105 кредита**. Значит кредит обязан быть дробным.

- **Хранение:** целое число микрокредитов, 1 мкр = 10⁻⁶ кредита.
  Никаких float в деньгах.
- **Отображение:** 2 знака после запятой, вниз для баланса, вверх для цены.
- **Совместимость:** `Transaction.amountUsd` в биллинге — `numeric(18,8)`,
  влезает без изменений.

### 5.3 Схема леджера

Дополняет существующие таблицы биллинга, не заменяет их.

```sql
-- Счёт арендатора. Баланс — производная от проводок, но материализован
-- для скорости и сверяется ночной задачей.
create table credit_accounts (
  tenant_id      uuid primary key,
  balance_micro  bigint not null default 0,
  updated_at     timestamptz not null default now()
);

-- Резерв под шаг. Живёт от старта шага до его конца.
create table credit_holds (
  id             uuid primary key,
  tenant_id      uuid not null,
  project_id     bigint not null,
  step_code      text not null,
  node_key       text,
  amount_micro   bigint not null,          -- по оценке p90
  state          text not null,            -- held | settled | released | expired
  expires_at     timestamptz not null,     -- страховка от зависшего шага
  created_at     timestamptz not null default now()
);

-- Проводка. Единственный источник правды по деньгам.
create table credit_entries (
  id             uuid primary key,
  tenant_id      uuid not null,
  hold_id        uuid references credit_holds(id),
  delta_micro    bigint not null,          -- + пополнение, − списание
  kind           text not null,            -- topup | settle | release | refund | adjust | promo
  cost_usd       numeric(18,8),            -- фактическая себестоимость операции
  margin         numeric(6,3),             -- применённая маржа (для аудита)
  ref_table      text,                     -- 'llm_calls' | 'media_calls'
  ref_ids        bigint[],                 -- какие именно вызовы оплачены
  created_at     timestamptz not null default now()
);

create index on credit_entries (tenant_id, created_at desc);
create index on credit_holds (tenant_id, state) where state = 'held';
```

`ref_table` / `ref_ids` смотрят в существующие журналы вызовов. Благодаря
этому по каждой списанной копейке видно, из каких вызовов она сложилась:
маржа считается по продукту, по клиенту и по шагу с первого дня, а не
задним числом.

### 5.4 Жизненный цикл: холд → списание → возврат

1. **Котировка.** Перед шагом считается оценка (см. §6.4). Пользователю
   показывается цена; агент не запускает шаг без явного согласия на дорогих
   шагах (порог — §7.3).
2. **Холд.** Резервируется **p90** оценки, не медиана. Проводка не создаётся,
   баланс уменьшается на сумму холда. Пользователь видит «зарезервировано».
3. **Исполнение.** Шаг пишет вызовы в `llm_calls` / `media_calls` как сейчас.
4. **Списание.** По завершении суммируется фактический `cost_usd` вызовов
   этого шага, умножается на маржу, создаётся `credit_entries(kind='settle')`,
   холд закрывается, **остаток возвращается на баланс той же операцией**.
5. **Отказ.** Шаг упал — холд снимается целиком (`kind='release'`).
   Пользователь не платит ни за одну попытку.
6. **Зависание.** `expires_at` прошёл, шаг не закрылся — холд освобождается
   фоновой задачей, шаг помечается сбойным. Деньги не зависают никогда.

Инвариант, который проверяется тестом: `balance = Σ delta_micro − Σ held`.
Расхождение — авария, а не «поправим потом».

### 5.5 Кто платит за брак

Владелец: «неудачных попыток не будет, всё будет отлажено». По журналам это
почти так, и вот точная цифра.

| Источник | Факт по журналам |
| --- | --- |
| Текстовые вызовы: отказ API, таймаут, исключение | 9 из 223 = **4.0%** |
| Контракт отбил ответ модели | 1 из 223 = **0.4%** |
| Медиа: отказ провайдера | **0** (два `error` в журнале — гашение бэкенда при рестарте) |

Падает дешёвое: 4% приходятся на текст, а текст — $0.87 из $5.53. Остаточный
брак ≈ **$0.02 на ролик**, то есть 0.4% себестоимости. При марже ×3 это
незаметно.

**Политика:** платформа съедает всё, что не является выбором пользователя.
Технически это уже обеспечено пунктом 5 жизненного цикла — холд снимается
целиком. Дополнительно:

- бюджет попыток на шаг (по умолчанию 2), после которого шаг честно
  объявляется несостоявшимся, а не крутится вечно;
- вызовы, оплаченные провайдером, но завершившиеся ошибкой (сегодня такой
  был один, $0.33), пишутся в `credit_entries(kind='adjust')` с нулевым
  `delta_micro` — не списываются с клиента, но видны в отчёте о марже.

### 5.6 Пополнение в рублях, расчёты в долларах

Решение владельца: пользователь платит рублями, конвертация происходит
**один раз — в момент пополнения**, после чего баланс и все списания живут в
долларах.

Это правильная конструкция, и вот почему: себестоимость у нас долларовая
(MiniMax, ElevenLabs), а выручка рублёвая. Если конвертировать при списании,
валютный риск висит на платформе всё время, пока кредиты лежат на балансе.
При конвертации в момент пополнения риск закрывается сразу: клиент купил
доллары по курсу дня, дальше курс никого не касается.

**Механика**

1. Пользователь выбирает пакет, видит цену в рублях.
2. YooKassa проводит платёж, `billing/payments` фиксирует `amount_kopecks`.
3. Курс берётся на момент подтверждения платежа и **записывается в проводку**.
4. На баланс зачисляется `amount_usd = amount_kopecks / 100 / rate`,
   проводка `credit_entries(kind='topup')`.
5. Чек по 422-ФЗ выставляется в рублях на фактически уплаченную сумму —
   это уже работает в `billing/receipts`, менять нечего.

**Курс.** Источник — ЦБ РФ на дату платежа, плюс наценка. Наценка не жадность,
а фактическая стоимость конвертации: карточный эквайринг и трансграничный
перевод к провайдерам съедают порядка 2–4%. Значение наценки — конфигурация,
не константа в коде.

**Что хранить в проводке.** Существующая `Transaction` в биллинге уже несёт
`amountUsd numeric(18,8)`, `amountKopecks bigint` и `meta jsonb` — этого
достаточно. В `meta` кладём:

```json
{ "fx_rate": 94.37, "fx_source": "cbr", "fx_markup": 0.03, "fx_at": "2026-08-23T09:00:00Z" }
```

Курс в проводке обязателен: без него нельзя ни разобрать спор с клиентом, ни
посчитать реальную маржу задним числом.

**Возвраты** — в рублях по курсу исходного пополнения, не текущему. Иначе
на движении курса возврат становится либо подарком, либо обманом.

**Отображение.** Баланс показывается в кредитах (то есть долларах), рядом —
справочный рублёвый эквивалент по текущему курсу с пометкой «примерно».
Цены шагов — только в кредитах: они долларовые по природе.

### 5.7 Бесплатный уровень: всё до первого видео

Решение владельца: бесплатно всё, что идёт до первой генерации видео.

**Экономика подарка.** Полная себестоимость доvideo-части:

| Часть | Себестоимость |
| --- | ---: |
| Текст (план → сценарий → сцены → промты) | $0.87 |
| Герои и предметы | $0.01 |
| 24 картинки | $0.084 |
| **Итого подарок** | **$0.97** |

Это 17% полного ролика. Человек получает готовую раскадровку — сценарий,
24 кадра, контактный лист — и платит только за рендер. Витрина честная:
качество видно до оплаты.

**Граница бесплатного.** Бесплатность действует **до первой оплаченной
генерации видео на аккаунте**. После неё все шаги любого проекта тарифицируются
обычным порядком. Формулировка «до первого видео» относится к аккаунту, а не к
каждому новому проекту: иначе подарок повторяется бесконечно и становится
$0.97 за каждый созданный проект.

**Предохранители — обязательны.** Бесплатная перегенерация картинок стоит
платформе денег, и без потолков это дыра:

| Ограничение | Значение по умолчанию |
| --- | --- |
| Проектов в бесплатном режиме | 1 |
| Кадров в бесплатном проекте | 24 |
| Бесплатных перегенераций картинок | 2 × число кадров (48) |
| Бесплатных перегенераций сценария/раскадровки | 2 |
| Потолок расхода на бесплатный аккаунт | $3.00, дальше требуется пополнение |
| Подтверждение почты | обязательно до старта первого шага |

Все счётчики ведутся в тех же `credit_entries` — проводками с нулевым
`delta_micro` и `kind='promo'`, где `cost_usd` заполнен фактической
себестоимостью. Это даёт отчёт «сколько стоит привлечение» без отдельной
подсистемы.

**Что видит пользователь.** «Раскадровка и кадры — бесплатно. Оплата только
за рендер видео: 13.68 кредита за 24 клипа». Момент оплаты наступает ровно
там, где ценность уже доказана.

| Один клип 1080P | $0.33 | **0.99** |
| Один кадр целиком (промт + картинка + клип 768P) | $0.2275 | **0.68** |
| Каскад: промты кадров → всё ниже | $4.79 | **14.37** |
| Каскад: камера → всё ниже | $4.89 | **14.67** |
| Каскад: сценарий → всё | $5.53 | **16.59** |

### 6.3 Ключевая пропорция продукта

```
одна картинка   $0.0035
один клип 768P  $0.1900     ← в 54 раза дороже
```

**Картинка дешевле клипа в 54 раза.** Отсюда вся конструкция интерфейса:
итерация происходит на кадрах, видео — одна финальная покупка. Конвейер уже
так устроен: HITL `approve_images` стоит перед генерацией видео.

### 6.4 Лестница уточнения оценки

Смета делится надвое, и это принципиально.

- **Детерминированная часть — медиа.** Как только известно число кадров,
  цена считается точно: `N × usd_per_call` из `media_prices.json`, где ключ —
  `провайдер:модель@разрешение:длительность`. Ошибиться нельзя.
- **Стохастическая часть — текст.** Зависит от числа вызовов; берётся медиана
  и p90 по историческим данным того же шага.

| Момент | Что известно | Точность оценки |
| --- | --- | --- |
| Пользователь описал тему | ничего | вилка ×2 |
| После сценария | символы → секунды → кадры (14 симв/с, кадр ≈ 2.9 с) | медиа точно, текст ±30% |
| Перед конкретным шагом | всё | точно |
| **Перед видео** | кадры × тариф | **точно, до цента** |

Самый дорогой шаг оказался самым предсказуемым: видео тарифицируется за
вызов, а не за токены.

### 6.5 Открытый пункт: озвучка

В `app/services/media_prices.json` у ElevenLabs стоит `null` — «тарифы
зависят от плана владельца, выдумывать их в коде нельзя». Учёт пишет вызов с
`unpriced=1` и денег не прибавляет.

**До запуска обязательно:** внести фактический тариф плана (за 1000 символов)
в прайс. Иначе озвучка бесплатна для пользователя и бесплатна в отчёте о
марже — то есть незаметно съедает прибыль. Объём: ~950 символов на ролик
70 секунд.

## 7. Перегенерация как продукт

### 7.1 Цена перегенерации — это радиус поражения, а не шаг

Разброс двадцатикратный: правка одного кадра стоит 0.68 кредита, а правка
сценария — 16.59. Пользователь, который «пошёл поменять промпт», должен
видеть, что именно сгорит, **до** нажатия.

Радиус считается по графу зависимостей шагов, который в системе уже есть.

### 7.2 Точечная перегенерация уже реализована

`app/services/hitl_apply.py`:

- `HITLDecision.regenerate` / `edit_prompt` на карточке картинок → кадр
  откатывается в `FrameStatus.image_prompt_ready`;
- то же на карточке видео → кадр откатывается в `animation_prompt_ready`.

Шаг доделывает **только откатившиеся кадры**. То есть ядро продукта —
«не понравился кадр, поменял промт, перерисовал один» — работает на уровне
данных. Не хватает чата поверх.

### 7.3 Правила интерфейса, вытекающие из цены

1. **Две кнопки, визуально разные.** «Перерисовать кадр — 0.01 кр» и
   «Переделать раскадровку — 14.67 кр» не должны выглядеть одинаково.
2. **Каскад — только через подтверждение** со списком того, что сгорает:
   «будут заново созданы 24 промта, 24 картинки и 24 клипа».
3. **Порог обязательного подтверждения — 1 кредит.** Всё дешевле выполняется
   сразу, дороже — спрашивает.
4. **Явная остановка перед видео.** Агент говорит: «раскадровка утверждена,
   24 клипа = 13.68 кредита, после этого правки станут дорогими».
5. **Пакет черновых клипов.** 512P втрое дешевле 1080P (0.30 против 0.99).
   Продавать как «черновой просмотр движения» перед финальным рендером.

## 8. Чат-агент и генеративный интерфейс

### 8.1 Готовое, что берём

Стек студии (Next 15, React 19, Radix, Tailwind, `@xyflow/react`,
TanStack Query) совпадает с тем, на что рассчитан **AI SDK**.

- `ai` + `@ai-sdk/react`: `useChat`, разбор `message.parts`, части вида
  `tool-<имя>` с состояниями `input-available` / `output-available` /
  `output-error`. Это и есть «агент ведёт по шагам с визуализацией»: шаг
  конвейера = инструмент агента, его результат = карточка в ленте.
- **AI Elements** — готовые компоненты чата в стиле shadcn (код копируется в
  проект): Conversation, Message, PromptInput, Task, Tool, Reasoning.
  У нас уже Radix + Tailwind + CVA, то есть соглашения shadcn.
- Канвас не выбрасываем: `@xyflow/react` остаётся второй панелью — слева
  разговор, справа живой граф.
- SSE в бэкенде уже есть (`app/web/routers/fleet.py`), прогресс шага течёт
  без опроса.

### 8.2 Жёсткое правило: агент — дирижёр, а не автор конвейера

Инструменты агента — тонкие обёртки над существующим
`POST /api/projects/{id}/steps/{code}/run`. Агент **не решает**, какие шаги
делать и в каком порядке: порядок задан конечным автоматом оркестратора.

Обоснование — весь разбор в `docs/SHOTS-FIX-2026-08-23.md` §11: пять
дефектов подряд имели одну форму, требование адресовали модели и не
проверили, что оно доехало. Дать LLM право строить конвейер — значит
воспроизвести этот класс дефектов на верхнем уровне.

### 8.3 Набор инструментов агента (первая версия)

| Инструмент | Что делает | Карточка в ленте |

## 10. Что готово и трогать не надо

Это капитал проекта, его не переписывать:

- **Сквозной конвейер.** Тема → скелет → сцены → шоты → промты → 24 кадра →
  24 клипа → озвучка → монтаж. Проверен живыми деньгами 2026-08-23.
- **Учёт до копейки.** `llm_calls` и `media_calls` пишут `cost_usd` по
  каждому вызову с моделью, нодой и результатом. Это готовый субстрат
  биллинга; обычно на него уходит месяц.
- **Приёмка среза** (`app/services/scene_design/acceptance.py`). Инвариант —
  одна запись: ключ, текст требования и функция проверки; текст уезжает в
  промт, функция в проверку. Именно это делает экономику сходящейся: после
  переноса `в_кадре` в код и починки payoff агент `action` стал проходить с
  первой попытки вместо пяти.
- **Расчёт присутствия и непрерывности кодом** (`presence.py`,
  `continuity.py`) — то, чего нельзя добиться промтом.
- **Гейт качества** — ruff, mypy в нуле, храповик падений тестов.
- **Точечная перегенерация** (`hitl_apply.py`) — ядро продуктовой петли.
- **`FleetNode` + `WorkLease`** — примитив распределения работы с атомарным
  захватом.

| Риск | Оценка | Что делаем |

| ToS провайдеров запрещает перепродажу | принят владельцем | см. ниже |

### Принятый риск: ToS провайдеров

Владелец 2026-08-23 принял риск осознанно, проверка ToS перед запуском не
проводится. Документ фиксирует, в чём именно экспозиция, чтобы решение
осталось решением, а не забытым допущением.

Ставка не в штрафе — её в таких ToS обычно нет. Ставка в **блокировке
аккаунта без предупреждения**, и бьёт она по времени: в момент блокировки
встают заказы всех клиентов сразу, деньги за них уже приняты, а перевод на
другого провайдера требует перекалибровки промтов (у MiniMax свои лимиты —
1500 символов на промт картинки, одна character-ссылка на кадр; на другом
провайдере эти ограничения другие).

**Смягчение, которое стоит дёшево и не требует пересмотра решения:**

1. Резервный провайдер на каждый вид генерации, проверенный заранее, а не в
   момент аварии. У `media_route` уже есть выбор провайдера по модели, а
   `img_pr_budget` считает лимит промта по фактическому генератору — то есть
   переключение архитектурно возможно уже сейчас.
2. Не держать на балансе у провайдера больше недельного расхода.
3. Мониторинг ответов 4xx с кодами блокировки — тревога владельцу, а не
   молчаливая остановка очереди.

### Требуют решения владельца

1. **Стартовый пакет кредитов** — размер и цена. Курс пополнения и наценка
   решены (§5.6), осталось назначить номиналы пакетов.
2. **Бренд и домен** видеостудии — от этого зависит значение `brand` в
   `User` и настройка Caddy.
