# Конституция — железные правила video-pipeline

**Дата:** 2026-09-04
**Тип:** ограничения. Нарушено — значит, есть ADR с причиной. «Я решил» не работает.

## Что это

Правила, которые не обсуждаются в каждом изменении. Они существуют, чтобы
не повторять уже оплаченные ошибки: каждое правило ниже написано после
конкретной поломки, ссылка на неё — в тексте правила.

Правила меняются только через ADR (`docs/adr/`), см. §«Как менять».
Машинные исполнители перечислены в `docs/ENGINEERING-POLICY.md`; правило
без исполнителя помечено «человеческое».

---

## Code rules — код

### CR-1: типы обязательны

`mypy app/ --ignore-missing-imports` зелёный. `# type: ignore` — только с
комментарием почему. Фронт: `tsc --noEmit` зелёный, `any` в новом коде
запрещён.

### CR-2: линт и формат не обсуждаются

`ruff check` и `ruff format --check` зелёные на всём репозитории.
Форматирование правит только `ruff format`, руками — никогда.

### CR-3: минимальное изменение

Не рефакторить то, что не просили. Один коммит — одно логическое
изменение. Массовое переименование и перенос файлов — отдельным коммитом,
без правок логики (иначе дифф нечитаем и ревью бессмысленно).

### CR-4: комментарий объясняет «почему», а не «что»

Пересказ кода запрещён. Комментарий уместен там, где решение неочевидно
или где уже наступали на грабли; ссылка на дату/коммит поломки приветствуется.

### CR-5: никаких литералов цвета вне токенов

Цвет живёт в `web/src/app/globals.css` (лист) или `studio-theme.css`
(студия). В компонентах — только токены. Исключение — каталоги студии
заказчика, они перечислены в гейте явным списком и список не растёт.

## Architectural rules — архитектура

### AR-1: база данных — единственный источник правды

DB v2 (`app/services/db_v2.py`, `db_apply.py`) — SoT для кадров, текстов и
промтов. `project.xlsx` — **экспорт**, не источник: любой шаг, читающий
xlsx как истину, чинится, а не обходится. Живой прогон 2026-08 показал,
что расхождение двух источников не ловится тестами и стоит целого ролика.

### AR-2: миграции совместимы в обе стороны (expand/contract)

Нумерованные, идемпотентные, тест на пустой и на унаследованной базе
(`tests/test_db_migrations.py`). Правка уже уехавшей миграции запрещена —
только новая. Деплой с миграцией — после бэкапа базы (§10 политики).

**Схема всегда на шаг совместима со старым кодом.** Откат прода — это
возврат образа на предыдущий дайджест, база при этом остаётся новой:
старый код обязан работать на новой схеме. Отсюда порядок: сначала
расширение (добавили колонку/таблицу, оба кода живут), релиз, и только
следующим релизом сужение (удалили старое). Разрушающая миграция в одном
релизе с кодом, который на неё опирается, запрещена — она делает откат
невозможным.

`downgrade` в ревизиях пишется и остаётся рабочим для локальной разработки,
но **откат прода через downgrade не выполняется**: путь отката — образ
(§7 политики), а не схема.

### AR-3: изоляция арендаторов на живом Postgres

RLS проверяется только на Postgres (`tests/test_rls_postgres.py`), на
SQLite политик не существует физически. Роль в тестах — обычная, не
суперпользователь: под суперпользователем RLS не действует, и тест
зеленел бы впустую. Уникальные ключи включают арендатора (0013).

### AR-4: граф ролика исполняется из `meta.canvas_graph`

Шаблон Workflow — заготовка для новых роликов, не исполняемая сущность.
Слой `project_graph` (diff → apply, предложение агента) — единственный
способ менять граф проекта; стадии — представление графа, не вторая
модель.

### AR-5: проверки без провайдера не зеленеют (fail-closed)

Без ключа check-роли падают, а не возвращают заглушку. Stub — только по
явному опт-ину `VP_ALLOW_STUB_CHECKS=1` для dev и тестов. Спека
`docs/openspec/specs/checks-cascade/spec.md`, Requirement 1.

### AR-6: библиотека промтов — вне git, источник в базе

`prompts/` намеренно в `.gitignore` и монтируется томом; на первом старте
импортируется в базу, дальше источник — `prompt_library`. Промты, которые
обязаны ехать в образ, лежат в `templates/`. Отсюда следствие: тест,
падающий на отсутствии промтов на чужой машине, — не регрессия
(`scripts/pytest_ratchet.py` это знает).

### AR-7: на проде нет браузера

Chrome/CDP на VPS не поднимается: нужен живой профиль с логинами. Прод
работает только через API-провайдеров, `OUTSEE_HTTP_FALLBACK_CDP=false`.
Код, который без CDP не работает, на проде считается сломанным.

### AR-8: деньги — по леджеру, без выдуманных чисел

Баланс = Σ delta − Σ held. Админу не выдаётся «бесконечный баланс»: у него
отсутствие кассы, шаг не тарифицируется вовсе. Ложь в леджере ломает
инвариант и перестаёт быть сигналом.

## Security rules — безопасность

### SR-1: `.env` не читать, не писать, не создавать

Ни агентом, ни лаунчером, ни кодом. Значения — только через окружение,
шаблоны — в `*.example` с пустыми значениями. Проверка наличия ключа —
grep по имени переменной, не по значению.

### SR-2: секретов в git нет никогда

`scan-secrets.py` на staged и на диффе, gitleaks в CI. Утёкший ключ
**ротируется**; удаление файла ротацию не заменяет — история остаётся.

### SR-3: ключи не светятся наружу

Ни в ответах API, ни в логах, ни в диагностических ручках. Отпечаток
ключа (`key[:4]…key[-4:]`) в ответе — тоже утечка: он сужает перебор и
подтверждает, какой ключ стоит.

### SR-4: API закрыт личностью

Ручки владельца недоступны арендатору; каждый адрес фронта отнесён либо к
продукту, либо к инструментам владельца (`tests/test_front_api_surface.py`).
Кнопка, ведущая в закрытую ручку, хуже отсутствующей.

### SR-5: PII и содержимое роликов не уезжают в чужие сервисы

Тексты, кадры и данные заказчика отправляются только тем провайдерам,
которые для этого выбраны. Диагностика третьим сторонам — без содержимого.

## Workflow rules — процесс

### WR-1: прод не трогаем руками

Не перезапускать контейнер, не править файлы на VPS, не «быстро поправить
на месте». Изменение едет только через релиз. Исключение — инцидент по
процедуре `docs/ENGINEERING-POLICY.md` §Инциденты.

### WR-2: спека впереди кода

Изменение контракта (API, схема БД, формат промта, поведение ноды) — сначала
`docs/openspec/changes/<id>/proposal.md` с решением и причиной, потом код.
Мелкий фикс без изменения контракта — без спеки.

### WR-3: ADR для архитектурных решений

Решение, которое переживёт одну задачу и свяжет руки в будущем, пишется в
`docs/adr/NNNN-<тема>.md`: контекст, решение, последствия, альтернативы.
Изменение этой конституции — только ADR.

### WR-4: гейт не обходится

`--no-verify`, `core.hooksPath`, `HUSKY=0` запрещены и закрыты guard'ом
агента. Красное чинится, а не гасится. Осознанное ослабление гейта —
решение владельца, записанное в спеку, с реестром долга.

### WR-5: долг только уменьшается

Любое исключение (diff-cov, hex-гейт, gitleaks-отпечаток, флаки-тест)
попадает в реестр с датой и причиной. Список исключений может только
сокращаться; рост — красный гейт.

### WR-6: чужой код не мержится вслепую

Перенос из форка заказчика или другого репозитория: сверка по файлам,
ревью панелью моделей, смоук, запись в спеку что взято и что нет — и
почему.

## Анти-паттерны — что точно нельзя

- Чинить симптом вместо причины (перезапуск вместо фикса, sleep вместо
  синхронизации, ретрай вместо разбора ошибки).
- Глотать исключение без разбора (`except Exception: pass` в рабочем пути).
- Тест, который проверяет мок, а не поведение; тест, дублирующий
  реализацию константой.
- «Временно» отключить проверку. Временное живёт дольше кода.
- Коммит с формулировкой «фиксы» — из сообщения должно быть понятно, что
  сломалось и почему так починено.
- Правка `web/out` руками и коммит собранной статики.
- Второй источник правды рядом с существующим (ещё один каталог моделей,
  ещё один парсер отчёта, ещё одна таблица статусов).

---

## Как менять эти правила

1. ADR в `docs/adr/`: что меняем, почему, чем это оплачено, что ломается.
2. Правка этого файла в том же коммите, что и ADR.
3. Если у правила есть машинный исполнитель — обновить его там же,
   иначе правило перестаёт быть правилом.
